状態：基本設計初稿。要件定義で合意した保存仕様に、構成・設定・処理フロー・検証方針を追加した。未解決事項は12節に集約する。

根拠は[要件定義書](requirements.md)とする。関数・モジュール・セレクター・内部形式の詳細は詳細設計で定める。既存の1～5節は保存・実行契約、7節以降はそれを実現する構成と処理方針を示す。実サイトは4記事と画像1件を限定調査済み（15・16節）。実装・exe検証は未実施。

## 1. Markdownの保存契約

[要件定義書](requirements.md) FR-08に基づき、参考アプリの[設計書7節・15.1節・15.2節](references/bl-documents-crawler/docs/design.md)のMarkdownファイル仕様を採用する。ただし、FR-09により階層別フォルダは使用しない。添付ファイルの保存は仕様変更により対象外とする。

- UTF-8・LFで保存し、先頭にYAMLフロントマターを置く。記事タイトルを先頭のH1とし、本文の同一タイトルを重複させない。見出し・表・リンクを維持し、サイト共通のヘッダー・メニュー・検索欄は本文から除外する。
- ファイル名は `タイトル-元URLのSHA-256ハッシュ先頭8桁.md`。別URLとの衝突時は4桁ずつ最大64桁まで延長し、それでも別URLと衝突する場合は異常終了する。元URL不明の破損ファイルとの衝突は10.4節の例外規則を適用する。
- URLの正規化はスキーム・ホストの小文字化とフラグメント除去に限定する。パスの大文字小文字・クエリ・末尾スラッシュは保持する。
- 参考仕様から引き継ぐフロントマターのキーは `title`、`source_url`、`fetched_at`、`created_at`、`updated_at`、`menu_path`、`content_hash`、`images` とする。`images` の各要素は `path` と `hash` を持ち、画像がなければ空配列とする。`attachments` は出力しない。
- 日時はタイムゾーン付きISO 8601形式。`created_at` は本アプリでの初版作成日時を保持する。`updated_at` は初回はnull、変更保存時は保存日時とする。`fetched_at` は保存データの取得日時で、無変更時には既存値を維持する。

破損により `created_at` を復元できない場合に限り、10.4節に従って再生成日時を使用する。
- 記事Markdownは保存ルート直下に配置し、メニュー階層でフォルダを分けない。`menu_path` は記事タイトルだけの配列（例：`["記事タイトル"]`）とし、メニュー階層は取得しない。
- 画像は保存ルートの `assets/<正規化した元URLのSHA-256全64桁>/` に、画像バイト列のSHA-256全64桁と種類に対応する拡張子で保存する。同じ記事の同一画像はまとめる。
- 本文の画像参照はMarkdownからの相対パス、`images[].path` は保存ルートからの相対パスとする。`images[].hash` は `sha256:<全64桁>` とする。
- `content_hash` は `sha256:<全64桁>`。計算対象は `タイトル + LF + 本文Markdown` のUTF-8表現とし、タイトルのH1記号とフロントマターを除く。画像参照は位置に依存しない画像ハッシュ識別子へ置換し、改行をLF、全体末尾の改行を1つに統一する。本文中の空白は一律に削除・圧縮しない。

## 2. 添付ファイルの扱い

添付ファイルは取得・保存しない。本文内の添付・ダウンロードリンクは通常のリンクとしてMarkdownに保持し、ローカルファイルへの相対参照に置換しない。添付欄を別途走査して一覧を追加する処理は設けない。画像の取得・保存は引き続き対象とする。

## 3. 再実行と更新

- 入力JSONの `is_new: true` のURLを再取得し、正規化した元URLで保存済み記事と対応付ける。
- タイトル・本文・画像に変更がある場合だけ既存ファイルを更新する。画像の追加・削除・差し替えも変更として扱う。
- 無変更時には既存Markdownと保存済み画像を上書きせず、フロントマターの日時も維持する。
- 更新時は `created_at` を引き継ぎ、`updated_at` に今回の保存日時を記録する。

## 4. 入力・保存先の指定と実行単位

- 入力JSONのファイルパスと保存先フォルダは外部設定ファイルで指定する。形式・名前・項目名は8.1節に定める。
- 取得対象URLは入力JSONに記載された順に処理する。
- 取得失敗時はその場で再試行せず、次回起動時に `is_new: true` のまま残っているURLを再処理する。
- URL一覧の各要素に必須項目の欠落や型の不正などがある場合は、当該要素をスキップして次のURLへ進む。不正要素は失敗件数に含め、ログに記録し、残りの対象を処理した後に異常終了する。全体停止条件を検出した場合はその時点で停止する。
- JSON全体の構文破損や `urls` 配列の欠落・型不正などによりURL一覧を読み取れない場合は、取得を開始せず、エラーを記録して異常終了する。
- 1回の実行で `is_new: true` の対象URLを一巡して終了し、自動的な繰り返し巡回は行わない。
- 途中位置を保持する再開機能は設けず、再実行時点で `is_new: true` のまま残っているURLを先頭から処理する。
- JSONは入力と処理状態の更新先を兼ねる。URLごとにMarkdown・画像の保存完了後、該当URLの `is_new` を `false` に書き戻す。一巡後まで書き戻しを保留しない。
- 書き戻しでは正常完了したURLの `is_new` だけを変更し、URL・配列の並び順・その他の項目と値を保持する。
- 再取得して変更なしと確認できた場合も正常完了として `false` にする。取得・保存失敗時には `true` のまま残す。
- JSONへの書き戻しに失敗した場合は、エラーを記録して全体を停止する。保存済みファイルは保持する。
- 入力JSONが読み取れ、入力不正などの失敗がなく、取得対象URLが0件の場合は処理件数0で正常終了する。不正要素がある場合は失敗として扱う。
- 一巡中に取得・変換・保存の失敗があった場合は残りの対象URLを処理したうえで異常終了する。ログイン切れ、JSONへの書き戻し失敗、HTTP 400および410～499による全体停止を優先する。
- 記事の処理完了後、次の記事へ進むまで基準待機時間にランダムな揺らぎを加えて待機する。既定値は基準180秒、揺らぎ±10秒とし、両方を外部設定ファイルで秒単位に変更可能とする。
- 取得に失敗して次の記事へ進む場合も、同じ基準待機時間とランダムな揺らぎを適用する。
- 記事・画像の取得でHTTP 401～409となった場合は当該記事をスキップし、エラーを記録して規定待機後に次の対象URLへ進む。記事の更新を見送り、`is_new` は `true` のまま保持する。これらの応答だけではログイン切れとして全体停止しない。一巡後は取得失敗ありとして異常終了する。
- HTTP 401～409以外の4xx（400および410～499）の場合は、当該記事の更新を見送り、`is_new` は `true` のまま保持する。エラーを記録して全体を異常終了し、次の対象URLへ進まない。

## 5. 取得範囲と同時実行

- 記事タイトルと記事内の全項目（質問・回答など）を保存し、ナビゲーション・関連記事・評価欄などは除外する。
- 同じ入力JSONまたは同じ保存先を使用する複数プロセスの同時実行を禁止する。ローカルでの防止方式と同期先を複数PCで使う場合の制約は13節に定める。

## 6. 設計の範囲と運用上の前提

- 要件定義書の合意済み要件と運用上の制約を根拠として具体化する。
- 本文・画像を実際のDOMで識別する方法。
- 保存対象の範囲は10.1節、既存成果物の扱いは10.4節、排他は13節に定める。

### 合意済みの補足方針

- 現在の入力JSONに `is_new: true` が残っている間は、次のURL一覧を生成・使用しない。取得を断念するURLはユーザーがログを確認し、手作業で `false` に変更して対象から外す。アプリは失敗URLを自動で `false` にしない。正常完了または手作業による対象除外で `true` がなくなった後、次のURL一覧を生成・使用する。
- 同じ記事の取得でHTTP 401～409とログイン画面の両方を検出した場合もスキップを優先する。これらの応答がない場合に、別の方法で確認したログイン切れによる全体停止を適用する。
- Markdown変換・ローカル保存失敗は記事単位で記録してスキップし、規定待機後に続行して一巡後に異常終了する。入力JSONへの書き戻し失敗は即時停止し、保存済みファイルを保持する。

## 7. 全体構成

1プロセスでURLを逐次処理する。並列取得・DB・定期実行基盤は設けない。Windows 11向けexeと外部設定ファイルを配布し、Chromeの起動とログインはユーザーが行う。

| 構成要素 | 責務 |
| --- | --- |
| 実行制御 | 入力順の処理、待機、スキップ・停止、終了結果の集計 |
| 設定・入力検証 | 設定読込、JSON全体と各要素の検証、対象選択 |
| ブラウザ取得 | ポート9223への接続、作業タブでの記事・画像取得、対象通信の判定 |
| 文書生成 | 本文抽出、Markdown変換、ローカル参照への置換、メタデータとハッシュ生成 |
| 成果物保存 | 元URLでの照合、変更判定、一時保存からの反映、既存ファイル管理 |
| 入力JSON更新 | 正常完了した要素の `is_new` の更新と安全な書き戻し |
| 運用出力・排他 | ログ、件数表示、入力JSONと保存先の同時使用防止 |

参考クローラーのPythonによる逐次処理と責務分割を基本方針とする。ブラウザ接続にはPlaywrightの同期APIとCDP接続、HTMLからの変換にはmarkdownify、exe化にはPyInstallerを採用する。JSON・TOML・ハッシュ・パス・待機はPython標準ライブラリで扱う。リポジトリ専用仮想環境を使い、Pythonと依存の版は環境構築時に確認して固定する。現時点では環境構築や依存追加は行わない。

Playwrightの[CDP接続](https://playwright.dev/python/docs/api/class-browsertype#browser-type-connect-over-cdp)は既存Chromiumブラウザに接続できるが、専用プロトコルより機能上の制限がある。[コンテキストのリクエストAPI](https://playwright.dev/python/docs/api/class-apirequestcontext)はCookieを共有する。画像1件の取得をPlaywriter経由で確認したため、認証付き画像取得の基本方式に採用する（17節）。別の認証方式を推測で追加せず、Python・exeでの再現確認を検証対象とする。

変換器は[markdownifyの公式配布情報](https://pypi.org/project/markdownify/)、exe化は[PyInstallerの使用方法](https://pyinstaller.org/en/stable/usage.html)を根拠とする。配布は単一exeを生成するonefile方式と外部 `settings.toml` を基本とし、Playwrightのドライバー等を含めPython未導入PCで検証する。自前のChromeを使い、Playwright用ブラウザの配布は前提にしない。公式資料確認日：2026-11-01。

## 8. 設定・入力契約

### 8.1 外部設定

設定ファイル名を `settings.toml` とし、exeと同じフォルダから読む。相対パスは設定ファイルの所在を基準とし、作業ディレクトリに依存させない。起動時に一度読み、認証値を格納しない。

| 項目案 | 用途 | 既定・制約 |
| --- | --- | --- |
| `input.json_path` | 更新対象でもある入力JSONのファイルパス | 必須。原本とは別の既存の作業用コピーを指定 |
| `storage.output_dir` | Markdown・画像の保存ルート | 必須。フォルダを指定 |
| `logging.error_dir` | エラーログの保存先フォルダ | 必須。成果物と分離 |
| `wait.interval_seconds` | 記事間の基準待機時間 | 180秒、0以上 |
| `wait.jitter_seconds` | 基準時間からのランダムな増減幅 | 10秒、0以上かつ基準以下 |
| `browser.connect_timeout_seconds` | Chrome接続の期限 | 初期案30秒、正の数 |
| `browser.page_timeout_seconds` | 記事表示・本文取得の期限 | 初期案60秒、正の数 |
| `browser.asset_timeout_seconds` | 画像1件の取得期限 | 初期案60秒、正の数 |

Chromeの接続先は `http://127.0.0.1:9223` とし、要件の固定ポートを設定で変更しない。待機時間は基準±揺らぎの範囲で待機ごとに抽選する。次の対象URLがない場合は記事間待機を行わない。タイムアウト値はサイト調査時に妥当性を確認する。

### 8.2 JSONの読込と保持

- ユーザーがURL一覧作成アプリの出力JSONを別の場所へコピーし、その作業用コピーを `input.json_path` に指定する。コピー作成は利用者の事前準備とし、本アプリの自動機能には追加しない。再実行には同じコピーを使用する。
- 原本と一覧作成アプリの `run-state.json` は変更しない。次回の一覧生成は原本を比較元とし、現在の作業用コピーに `true` が残っていないことを利用者が確認してから実行する。
- 入力はURL一覧作成アプリのUTF-8 JSONを使用する。`urls` 配列内の正常な要素は、空でない文字列 `url` とJSON真偽値 `is_new` を持つ。
- JSONを解析できない、最上位がオブジェクトでない、`urls` が配列でない場合は取得開始前に異常終了する。
- 不正要素は配列内の位置と理由をログに記録し、1要素を失敗1件として保持したままスキップする。値を推測して補完・修復しない。
- `is_new: false` の正常要素は取得しない。`true` の正常要素は配列順に処理する。
- 元URLは入力の表記を保持する。成果物の同一性・命名には1節の正規化を使用する。
- 未知の項目も含めJSONの値と配列順を保持し、正常完了した要素の `is_new` だけを変更する。空白・インデントなどのテキスト表現の維持は必須としない。
- 対象記事URLは参照アプリの出力に合わせ、HTTPS、ホスト `blackline.my.site.com`、パス `/BlackLineCommunity/s/article/` 配下、ユーザー情報・クエリ・フラグメントなしとする。異なる形式は当該要素の不正としてスキップし、別形式へ推測で修正しない。この制約は記事URLの検証であり、画像の配信先を同じホストへ限定するものではない。
- 重複JSONキーは、保持すべき値を一意に決められないためJSON全体の読込失敗として扱う。NaN等の非標準JSON値も受け付けない。
- `schema_version`、`source_url`、`article_type`、`collected_at` は受け渡し元のメタデータとして保持し、取得対象の選択には使用しない。消費する `urls`・`url`・`is_new` 以外の項目の欠落だけでは、対象URLをスキップしない。将来、構造の異なる版に対応する場合は契約を見直す。
- 配列内の同じURLを自動削除・並べ替えしない。各要素を入力順に扱い、正常完了した要素だけを更新する。同じ記事が複数回対象となった場合も通常の既存比較を行う。

## 9. 実行フローとブラウザの使用

1. 設定を読み、入力・保存先・ログ先のパスを検証する。
2. 入力JSONと保存先の排他を13節に従って確保する。WindowsのOS管理のファイルロックを用い、終了時に解放する。ロック識別・取得順・パス同一性の具体的な実装は詳細設計で定める。
3. 入力JSONを解析し、正常要素と不正要素を識別する。保存済みMarkdownを元URLで照合できるよう確認する。
4. 取得対象があればChromeへ接続し、ユーザーの既存タブと分離した作業タブで対象URLを開く。既存タブやChrome全体は閉じない。
5. 記事のタイトル・本文全項目と、画像を取得する。ログイン画面やエラーHTMLを記事・画像として保存しない。
6. 一時領域でMarkdown・資産・ハッシュを生成して既存内容と比較し、新規保存・更新・変更なしを判定する。
7. 保存または変更なし確認が成功した要素だけ、入力JSONの `is_new` を `false` に書き戻す。
8. スキップ時は失敗を記録し、入力の状態を維持する。全体停止条件がなければ、次の対象URLの前に規定待機する。その場で再取得しない。
9. 終了時に作業タブ・接続・排他を解放し、件数と終了結果を表示する。

記事・画像に関係する通信だけを判定し、広告・計測など無関係な通信の4xxで記事を停止・スキップしない。通信と対象記事との対応方法、本文の完成判定、遅延読み込み・転送の観測条件は、実際の構造確認後に確定する。

| 事象 | 基本動作 |
| --- | --- |
| 対象通信の401～409 | 記事をスキップ。ログイン画面も検出した場合も同じ |
| 対象通信の400・410～499 | 全体を異常終了 |
| 上記スキップ応答がなくログイン切れを確認 | 全体を異常終了、自動ログインしない |
| その他の取得失敗、変換失敗、成果物保存失敗 | 記事をスキップし、待機後に次へ |
| 入力JSONの更新失敗 | 保存済み成果物を保持して全体を異常終了 |

## 10. 保存・変更判定・JSON書き戻し

### 10.1 保存対象の範囲

保存対象は記事Markdownと本文画像とする。添付保存用ディレクトリ、添付用メタデータ、添付バイト列の変更検出は設けない。本文内リンクの文字列・参照先の変更は本文の変更として扱うが、リンク先のファイル内容は比較しない。

### 10.2 変更判定と反映

- 元URLで同じ記事を特定し、タイトル・本文・画像一覧とバイト列を比較する。日時だけでは変更としない。
- 無変更時は既存成果物と日時を維持する。タイトル変更時も同じURLの初版作成日時を引き継ぐ。
- 同期対象外のローカル一時領域で生成と取得を完了してから、資産、Markdownの順に最終反映する。既存Markdownへ直接書きかけの内容を保存しない。
- 最終保存先と同じファイルシステムに一時ファイルを置き、書込完了後に置換する。複数ファイルとクラウド同期をまとめたトランザクションは保証しない。
- 途中失敗時は `is_new` を変更しない。途中反映済みの資産、改名途中、管理ファイル破損などの検出と復旧方針は10.4節に定める。

### 10.3 入力JSONの更新

正常完了した要素の `is_new` を変更したJSONを、入力JSONと同じフォルダの一時ファイルへUTF-8で保存し、再読込検証後に置換する。変更前の入力JSONへ直接書き込まない。URLごとに置換を完了してから次へ進む。

読込後に別プロセス・手作業で入力が変更されていないことを、書き戻し直前に確認する。変化を検出した場合は上書きせずJSON更新失敗として停止する。外部編集との競合保証範囲は排他方式と合わせ詳細設計で定める。

成果物保存後・JSON更新前の中断では、成果物が存在しても `true` が残る。再実行時は再取得・比較し、変更なしを確認してから `false` にする。

### 10.4 既存成果物・改名・途中失敗からの復旧

既存記事の識別はMarkdownの `source_url` による。ファイル名やタイトルだけで同じ記事と判断しない。保存ルート直下のアプリ生成Markdownを対象に対応表を作り、資産配下や一時ファイルは記事として走査しない。DBや途中位置の保存は追加しない。

タイトル変更時は、新タイトルのファイル名でMarkdownを保存・検証してから、同じURLの旧Markdownを削除する。`created_at` を引き継ぎ、`menu_path` を新タイトルだけの配列へ更新する。旧ファイルの整理が完了するまで入力JSONを `false` にしない。別URLのファイルは削除しない。

| 失敗・残留状態 | 再実行時の扱い |
| --- | --- |
| 資産だけ反映済み、Markdownは旧版または未作成 | 再取得して通常の比較・保存を行う。既存資産の内容ハッシュを実バイト列で検証し、一致すれば再利用する |
| Markdown保存済み、入力JSONは `true` | 再取得・比較し、変更なしまたは変更保存が正常完了してから `false` にする |
| 改名後の旧Markdown削除失敗 | 当該記事の保存失敗として記録し、`true` を維持する。再実行時は同一URLの重複として再取得・上書きの対象とし、重複そのものを理由に全体停止しない |
| 一時ファイルだけが残存 | 完成Markdownとして扱わない。実行識別子付きの一時名を使い、他の実行の残留物を無条件に削除しない |
| 参照先の資産が欠落・ハッシュ不一致 | 無変更扱いにせず、対象記事の再取得・保存で修復する。再取得に失敗した場合は未完了のまま残す |

不要となった旧画像は自動削除しない。記事単位の反映済みファイルを失敗時に一括ロールバックしない。これは参照切れを避け、再実行で比較できる状態を残すためである。元記事の削除や入力対象外化を理由とする保存済み成果物の削除も行わない。

既存Markdownの破損や同じURLの複数Markdownを検出した場合は、それだけを理由に全体停止せず、対象記事を再取得して上書きする。破損状態を無変更扱いにはしない。再取得・保存が失敗した場合は通常の記事単位の失敗として扱う。

同一URLとの照合ができる正常なメタデータは引き継ぐ。同一URLの複数候補に有効な `created_at` があれば、タイムゾーンを考慮して最も早い日時を保持する。どの候補からも復元できない場合は今回の再生成日時を `created_at` とする。既存記事の修復では `updated_at` にも今回の保存日時を記録する。

同一URLの重複は現在のタイトルに対応する1ファイルへ再生成し、新版保存・検証後に、同一URLと確認できた他のMarkdownを削除する。削除が失敗した場合は記事の保存失敗として `true` を維持し、規定待機後に後続記事へ進む。同じURLでも無変更判定を理由に重複整理を省略しない。

`source_url` を読めない破損ファイルは、ファイル名やハッシュの短い接尾辞だけで入力URLと対応付けず、そのまま保持する。取得記事の通常の保存名と衝突する場合は、URLハッシュを8桁から4桁ずつ延長して別名にする。全64桁でも保存名が占有されている場合は、破損ファイルを上書きせず、この識別不能ファイルとの衝突に限り一意な接尾辞を付ける。次回は新しい正常ファイルの `source_url` で照合し、毎回別ファイルを作らない。具体的な接尾辞形式は詳細設計で固定する。

破損ファイルを残して別名保存するだけの場合は、新しく保存した記事の `created_at` を今回の保存日時、`updated_at` をnullとする。修復または対象不明ファイルを保持した事実と日時の再設定は、認証値を含めない診断情報として記録する。保持ファイル自体を元URL不明のまま成功・失敗件数へ追加しない。

## 11. ログ・終了・検証と配布確認

- 新規保存・更新・変更なし・失敗を11.1節の定義で表示する。完了記録まで成功した場合だけ成功件数に含める。
- エラーログは実行単位で分離し、日時・入力要素の位置・処理段階・理由・HTTPステータスを記録する。Cookie・認証ヘッダー・トークン・ページ本文を記録しない。URLは秘密値を除いた識別情報とする。
- 正常終了は終了コード0、失敗ありまたは全体停止は終了コード1を基本とする。手動中断の終了コードは詳細設計で定める。
- 保存ルートに記事Markdownと資産、ログ先に運用出力を置く。参考アプリ固有の監視用完了日時ファイルは、今回の要件へ自動追加しない。

| 検証対象 | 確認内容 |
| --- | --- |
| 入力・設定 | 真偽値の厳密判定、不正要素と全体破損、空配列、未知項目と順序保持、パス基準 |
| 取得 | ダミー画面で本文境界、画像、ログイン画面、対象通信と無関係な通信を分離 |
| エラー制御 | 401～409、400・410～499、その他取得失敗、変換・保存失敗、ログイン切れの優先順位 |
| 保存・更新 | 新規・無変更・本文更新・画像更新、元URL照合、日時維持、ファイル名衝突 |
| 完了記録 | URLごとの書き戻し、JSON更新失敗、外部変更検出、保存後・JSON更新前の中断 |

通常の検証はモック・ダミー資料で行う。実サイトの読取確認は対象・保存場所を明確にして別途実施し、既に実施済みとは扱わない。PROD更新リクエストによるテストは行わない。

### 11.1 件数の定義

集計単位は入力配列の各要素とし、重複URLも要素ごとに数える。次の4分類は重複させない。

| 表示分類 | 条件 |
| --- | --- |
| 新規保存 | 対応する既存記事がなく、成果物保存と `is_new: false` の書き戻しが成功 |
| 更新 | 対応する既存記事に変更があり、成果物更新・必要な旧Markdown整理・JSON書き戻しが成功 |
| 変更なし | 取得・比較で無変更を確認し、JSON書き戻しが成功 |
| 失敗 | 不正要素、取得・比較・変換・保存失敗、当該要素のJSON書き戻し失敗 |

正常な `is_new: false` の要素と、全体停止後の未着手要素は4分類に含めない。JSON全体の破損・設定不備など対象要素を特定できない障害は実行全体のエラーとして表示し、URL失敗件数へ架空の1件を加えない。4分類がすべて0でも異常終了する場合がある。

成果物保存後にJSON更新が失敗した場合は、当該要素を失敗1件とし、新規保存・更新・変更なしには加えない。ログには成果物反映済み・完了記録未反映の段階を記録する。既に完了した先行要素の成功件数は維持する。強制終了・PC停止時の最終件数表示は保証しない。

### 11.2 ログ出力契約と障害時の動作

ログはUTF-8のJSONとし、エラー1件につき1ファイル、日時と実行識別子・一意な接尾辞で命名する。既存ログを上書きしない。項目は `occurred_at`、`run_id`、`input_index`、`source_url`、`stage`、`error_code`、`http_status`、固定文の `message` を基本とする。値を特定できない項目はnullとし、生の例外文字列や通信内容は保存しない。

ログ保存自体の失敗時は次のとおり処理する。

1. 指定ログ先への出力失敗時は、同期対象外の `%LOCALAPPDATA%/BlackLineKnowledgeCrawler/fallback-errors/` への代替保存と標準エラー表示を試みる。
2. 代替保存の成否にかかわらず全体を異常終了する。失敗履歴を指定先へ残せないまま後続URLを処理しない。
3. 失敗の通知が再帰的にログを生成しないようにする。すべてのファイル出力が失敗した場合は、画面で記録不能と停止理由を示す。

ログ保存の失敗で既に書き戻し済みの `false` を `true` に戻したり、成果物を削除したりしない。

## 13. 排他と保存先の利用範囲

同一PCでは、入力JSONと保存ルートにそれぞれ対応するロックファイルを用い、実行中はOSの排他ロックを保持する。対象のJSON本体は置換更新されるため、それ自体だけをロック対象にしない。ロックファイルの存在だけで起動禁止とは判断せず、プロセス終了時にはOSによって保持ロックが解放される方式とする。

- 入力JSONが同じなら保存先が違っても同時実行しない。保存先が同じなら入力JSONが違っても同時実行しない。
- すべてのロックを確保してからJSON読込・成果物変更を始める。取得順を固定し、確保できなければ待機して巡回を開始せず、起動エラーとして異常終了する。
- 絶対パス化、既存親の解決、大文字小文字やリンクによる同一実体の確認方法は詳細設計で定める。別名パスによる排他漏れを検証する。
- 手作業による入力編集は実行停止中に行う。ロックを尊重しない外部エディターによる同時編集を完全には防げないため、書き戻し前の変更検出も併用する。
- ローカルのOSロックはOneDrive等の同期によって別PCへ共有されない。同じクラウド上の保存先・作業用JSONを別PCから同時に変更しないことは、利用者の運用上の制約とする。複数PC間の分散ロックは追加しない。

## 15. 実サイト限定調査を踏まえた取得方針

2026-11-01にPlaywriterで実施した[記事読取調査](knowledge-article-observations.md)を根拠とする。Playwriterは今回の調査ツールであり、配布アプリのPython・Playwright方式を変更するものではない。

- 2記事で、記事コンポーネント内のタイトルと本文領域を一意に識別できた。本文の項目ラベルと内容を入力順に保持し、Question・Answerだけに固定しない。記事内部の `Related To` は本文項目として扱い、外部の関連記事一覧と混同しない。
- 評価欄は本文領域外にあり、本文コンテナに限定することで除外できる。空の非表示項目は保存しない。非表示に実データが存在する場合の扱いは追加調査で判断する。
- `DOMContentLoaded` のみを完了条件にしない。タイトル・本文領域の一意性と可視状態を確認してから、本文・画像一覧の安定確認へ進む。16節にAPI照合と安定条件を定め、17節に追加確認の結果と適用限界を記載する。
- 画像の応答ヘッダーとバイト列の形式が不一致となる例を観測した。保存拡張子は対応形式の実データ署名とデコード結果を根拠に決める。ヘッダーの不一致だけで取得失敗にせず、HTML・認識不能な内容・デコード不能な内容は画像として成功扱いにしない。対応形式と検証方法は詳細設計で固定する。
- 当該画像は同一オリジン・ページ内GETと、後続調査のコンテキストリクエストAPIの両方で200応答を確認した。Python・exeでの確認とは区別する（17節）。
- 添付ファイルの保存は廃止済みのため、添付欄・ダウンロード方式の調査は設計確定の条件にしない。

今回の観測を使い、本文項目・表・画像形式不一致のダミー資料を後続検証用に作成する。認証情報や実記事全文をそのままfixture化しない。

## 16. 記事APIの対応付けと取得完了条件

### 16.1 適用範囲

[追加調査記録6節](knowledge-article-observations.md#6-記事apiの追加調査)で確認したQA記事のフィールドセット表示に対する設計とする。サイト側に内部APIを直接再送する処理は設けず、ブラウザの通常遷移に伴う通信を観測する。未確認の別表示形式に推測で適用しない。

### 16.2 通信の照合

1. URLへ移動する前に、その作業タブの通信監視を開始し、取得回ごとの識別子を付ける。前の記事の応答を流用しない。
2. 対象URL末尾の `urlName` に対応する `getArticleVersionId` の要求を選び、Auraの要求アクションIDと応答アクションIDを結び付けて、成功した記事版IDを確定する。同じURLに複数応答がある場合は結果の一致を確認する。
3. 解決した記事版IDを引数に持つ `getKnowledgeArticle` を対応付ける。成功応答の `articleId` と要求ID、`title` と描画タイトルを照合する。
4. 同じ記事版IDと記事情報の `recordTypeName` を引数に持つ `getFieldSetData` を対応付け、アクション単位の成功を確認する。応答内の `articleId`・`title` が空の場合は、要求引数とAuraのアクションIDによる照合を用いる。
5. 非空の識別情報が返った場合は矛盾がないことを確認する。観測で空だった `urlName` だけを根拠に別URLと判定しない。

Auraは1つのHTTP応答に複数アクションを含むため、HTTP 200だけでは記事取得成功としない。対象アクションの失敗は記事取得失敗として扱う。別アクションの失敗を対象記事の失敗と推測しない。通信エラーのHTTPステータスが判明する場合は、要件の401～409スキップ・その他4xx停止を優先する。

監視するのは対象の作業タブと、その回の対象要求である。ユーザーの既存タブ・別記事・プロフィール・ナビゲーション用通信は記事の成功判定に使わない。Cookie・トークン・要求本文全体をログや管理ファイルに保存しない。

### 16.3 本文の完成判定

QAフィールドセット表示では、少なくとも次の条件を同一ページ取得期限内で満たしてから保存候補を作る。

- 対象URLに留まり、記事コンポーネント・タイトル・本文が一意で可視になっている。
- 16.2節のID解決・記事情報・本文項目が成功し、相互の対応が成立している。
- 本文項目の順序・ラベル・値辞書を取得でき、描画された項目との対応を確認できる。値がない項目を無理に必須とせず、Question・Answer以外も保持する。APIに非空の値がある項目がDOMから取得できない場合は、ラベルだけを保存して成功としない。
- HTML・テキスト・画像参照のスナップショットが、250ms間隔の連続2回で一致する。これは描画開始直後の取りこぼしを減らす条件であり、将来の更新を保証しない。
- 採用する画像の読込・実データ取得が完了し、取得後にも本文と画像参照が保存候補から変わっていない。

安定確認の250msは記事間待機の設定と区別する。同じページの完成待ちは再取得リトライではない。本文の初期描画中の変化は、ページ取得期限内で再度スナップショットを採って安定を待つ。期限切れ・API不一致、または保存候補の確定後の本文変更は、その場でページを再読込せず記事をスキップする。

本文とAPI値の比較では、HTMLエンティティ・リッチテキストのラッパー等の差を考慮する必要がある。比較用の正規化規則はダミー資料と追加観測で検証し、詳細設計に固定する。安定したDOMが存在するだけで、APIに含まれる本文を省略した状態を正常完了にしない。

### 16.4 残る実証と限界

記事APIの対応付けは1記事での限定確認であり、全URL・全言語の受入完了ではない。次を確認してから、サイト固有条件を設計確定とする。

- 複数画像・遅延読込・値のあるAdditional Informationでの本文とAPIの対応。
- ログイン切れ、転送、対象アクション失敗を識別する応答と画面。
- Python版Playwrightでの要求・応答の相関、画像取得、250msの安定条件の妥当性。

現時点で未確認の別表示形式を、成功扱いの推測で埋めない。添付ファイルの取得は成功判定の対象外とする。

## 17. 画像取得方式・待機期限・未確認ケース

### 17.1 HTTP画像の取得

[調査記録7節](knowledge-article-observations.md#7-画像取得方式と本文安定の追加確認)に基づき、既存コンテキストの `request.get` を基本とする。ブラウザの選択した `currentSrc` を優先し、未設定の場合だけ `src` を用いる。相対参照は記事URL基準で解決する。本文外のロゴ・プロフィール画像・評価アイコンは保存対象にしない。

Cookieをファイルへ書き出さず、別のHTTPクライアントへコピーしない。画像URLに必要なクエリを取得時に削除せず、その値をログやフロントマターへ保存しない。Markdownと `images` にはローカルの相対参照・内容ハッシュを記録する。

APIRequestContextの[GETオプション](https://playwright.dev/python/docs/api/class-apirequestcontext#api-request-context-get)を使い、通信の自動再試行を行わず、HTTPエラーでも応答ステータスを取得して要件の規則へ振り分ける。転送の自動追跡は無効にし、転送応答は画像取得失敗として記事をスキップする。今回の確認画像は転送なしで取得できた。認証画面の200応答を画像として保存しない。確認日：2026-11-01。

画像バイト列は一時領域へ取得し、形式と内容ハッシュを検証してから最終配置する。1件の画像取得に失敗した場合は、その画像を欠いた記事を完成扱いにしない。失敗時に別方式へ自動切替したり、同じURLを再送したりしない。API応答オブジェクトと不要なバイト列は処理後に解放する。

### 17.2 画像の表示・本文の安定と期限

画像1件で `complete` が真、自然寸法が正、`currentSrc` と `src` の一致を確認した。`complete` だけで成功とせず、ブラウザでの読込状態と取得バイト列の両方を検証する。250ms間隔の本文HTML一致も1例で確認したが、この値で将来の表示変更を完全に検出できるとは扱わない。

`page_timeout_seconds` はURL移動・記事API・タイトルと本文描画・初回の安定確認をまとめた共通の期限とし、待機処理ごとに60秒を加算し直さない。初回の保存候補を確定した後、各画像の取得にはそれぞれ `asset_timeout_seconds` を適用する。画像取得後は保存候補のタイトル・本文・画像参照と現在のDOMを照合し、変化していれば再取得せず失敗にする。

遅延読込を起動する必要がある場合は、作業タブの記事本文内で対象画像を表示位置へ移動し、選択された画像参照が確定するのをページ取得期限内で待つ。本文外のリンクを開いて画像を探さない。参照未確定・読込失敗・APIとDOMの非整合を、単に安定したという理由だけで成功としない。

### 17.3 未確認形式の扱いと次工程

HTTP画像・通常のフィールドセット本文は上記契約で設計する。data URI・blob URL・SVG・埋込フレーム内の記事本文など、今回の調査で取得手順を確認していない形式が実際に現れた場合は、対応方式を詳細設計で検証する。対応できない場合は黙って省略せず、記事の取得失敗としてログに記録し `true` を保持する。

ログイン切れの判定は、対象記事の表示失敗だけで推測しない。401～409をスキップする要件を維持し、それ以外のログイン切れ画面・転送先の具体的な識別条件は、匿名化資料または限定観測を根拠に詳細設計で固定する。実際のアカウントをログアウトさせたりCookieを削除したりする調査は行っていない。

次工程では、実装前にダミー応答による対象API相関と画像形式不一致の確認、API値とDOMの比較正規化、Python版の取得方式、特殊形式・ログイン画面の判定条件を詳細設計へ記録する。基本設計から先行して本番クローラーを実装したとは扱わない。
