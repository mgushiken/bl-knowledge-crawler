# 基本設計書 — BlackLine Knowledge 取得アプリ

状態：要件定義中の部分草案。ユーザーから指定された保存仕様のみ記録する。

## 1. Markdownの保存契約

[要件定義書](requirements.md) FR-08に基づき、参考アプリの[設計書7節・15.1節・15.2節](references/bl-documents-crawler/docs/design.md)のMarkdownファイル仕様を採用する。ただし、FR-09により階層別フォルダは使用せず、FR-10により添付ファイルの保存を追加する。

- UTF-8・LFで保存し、先頭にYAMLフロントマターを置く。記事タイトルを先頭のH1とし、本文の同一タイトルを重複させない。見出し・表・リンクを維持し、サイト共通のヘッダー・メニュー・検索欄は本文から除外する。
- ファイル名は `タイトル-元URLのSHA-256ハッシュ先頭8桁.md`。別URLとの衝突時は4桁ずつ最大64桁まで延長し、それでも衝突する場合は異常終了する。
- URLの正規化はスキーム・ホストの小文字化とフラグメント除去に限定する。パスの大文字小文字・クエリ・末尾スラッシュは保持する。
- フロントマターのキーは `title`、`source_url`、`fetched_at`、`created_at`、`updated_at`、`menu_path`、`content_hash`、`images` とする。`images` の各要素は `path` と `hash` を持ち、画像がなければ空配列とする。
- 日時はタイムゾーン付きISO 8601形式。`created_at` は本アプリでの初版作成日時を保持する。`updated_at` は初回はnull、変更保存時は保存日時とする。`fetched_at` は保存データの取得日時で、無変更時には既存値を維持する。
- 記事Markdownは保存ルート直下に配置し、メニュー階層でフォルダを分けない。`menu_path` は記事タイトルだけの配列（例：`["記事タイトル"]`）とし、メニュー階層は取得しない。
- 画像は保存ルートの `assets/<正規化した元URLのSHA-256全64桁>/` に、画像バイト列のSHA-256全64桁と種類に対応する拡張子で保存する。同じ記事の同一画像はまとめる。
- 本文の画像参照はMarkdownからの相対パス、`images[].path` は保存ルートからの相対パスとする。`images[].hash` は `sha256:<全64桁>` とする。
- `content_hash` は `sha256:<全64桁>`。計算対象は `タイトル + LF + 本文Markdown` のUTF-8表現とし、タイトルのH1記号とフロントマターを除く。画像参照は位置に依存しない画像ハッシュ識別子へ置換し、改行をLF、全体末尾の改行を1つに統一する。本文中の空白は一律に削除・圧縮しない。

## 2. 添付ファイルの保存

- 記事に添付されたファイルを元の形式でローカル保存する。
- Markdown内の添付ファイルへのリンクは、Markdown所在を基準としたローカルの相対パスに置換する。
- 配置・命名・衝突回避・メタデータの詳細は今後の設計で定める。

## 3. 再実行と更新

- 入力JSONの `is_new: true` のURLを再取得し、正規化した元URLで保存済み記事と対応付ける。
- タイトル・本文・画像・添付ファイルに変更がある場合だけ既存ファイルを更新する。画像・添付ファイルの追加・削除・差し替えも変更として扱う。
- 無変更時には既存Markdownと保存済み画像・添付ファイルを上書きせず、フロントマターの日時も維持する。
- 更新時は `created_at` を引き継ぎ、`updated_at` に今回の保存日時を記録する。

## 4. 入力・保存先の指定と実行単位

- 入力JSONのファイルパスと保存先フォルダは外部設定ファイルで指定する。設定ファイルの形式・名前・項目名は今後の設計で定める。
- 1回の実行で `is_new: true` の対象URLを一巡して終了し、自動的な繰り返し巡回は行わない。
- 途中位置を保持する再開機能は設けず、再実行時点で `is_new: true` のまま残っているURLを先頭から処理する。
- JSONは入力と処理状態の更新先を兼ねる。URLごとにMarkdown・画像・添付ファイルの保存完了後、該当URLの `is_new` を `false` に書き戻す。一巡後まで書き戻しを保留しない。
- 再取得して変更なしと確認できた場合も正常完了として `false` にする。取得・保存失敗時には `true` のまま残す。
- JSONへの書き戻しに失敗した場合は、エラーを記録して全体を停止する。保存済みファイルは保持する。
- 取得対象URLが0件の場合は処理件数0で正常終了する。
- 一巡中に取得失敗があった場合は残りの対象URLを処理したうえで異常終了する。ログイン切れ、JSONへの書き戻し失敗、HTTP 400および410～499による全体停止を優先する。
- 記事の処理完了後、次の記事へ進むまで基準待機時間にランダムな揺らぎを加えて待機する。既定値は基準180秒、揺らぎ±10秒とし、両方を外部設定ファイルで秒単位に変更可能とする。
- 取得に失敗して次の記事へ進む場合も、同じ基準待機時間とランダムな揺らぎを適用する。
- 記事・画像・添付ファイルの取得でHTTP 401～409となった場合は当該記事をスキップし、エラーを記録して規定待機後に次の対象URLへ進む。記事の更新を見送り、`is_new` は `true` のまま保持する。これらの応答だけではログイン切れとして全体停止しない。一巡後は取得失敗ありとして異常終了する。
- HTTP 401～409以外の4xx（400および410～499）の場合は、当該記事の更新を見送り、`is_new` は `true` のまま保持する。エラーを記録して全体を異常終了し、次の対象URLへ進まない。
