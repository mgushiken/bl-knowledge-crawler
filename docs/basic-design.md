# 基本設計書 — BlackLine Knowledge 取得アプリ

更新日：2026-11-01

状態：基本設計レビュー・マージ完了。詳細設計開始後の終了処理の合意を反映済み。検証状況と次工程への引継ぎは12節に記載する。

## 1. 根拠・対象範囲

要件の正本は[要件定義書](requirements.md)とする。本書は構成、設定、外部入出力、取得・保存契約、異常時の処理方針を定める。モジュール・関数・セレクター・比較正規化・内部状態形式は詳細設計で具体化する。

URL一覧作成アプリの出力をユーザーが作業用JSONへコピーし、その `is_new: true` のURLだけをブラウザで取得する。記事Markdownと本文画像をローカル保存し、URLごとに完了状態をJSONへ書き戻して、一巡で終了する。

添付ファイルの取得・保存は対象外とする。本文内の添付・ダウンロードリンクは通常のリンクとして保持し、ローカル参照へ置換しない。添付欄の別途走査、添付一覧の追加、添付メタデータ・変更検出は設けない。通常のWebページへのリンク先も巡回しない。

参考クローラーの[設計書7・15節](references/bl-documents-crawler/docs/design.md)のMarkdown仕様を踏襲する。ただし、階層分け・`menu_path`・破損修復は本アプリの要件を適用する。参考アプリの監視用完了日時ファイルや繰り返し巡回は追加しない。

## 2. 全体構成・採用技術

1プロセスでURLを逐次処理する。並列取得・DB・定期実行基盤・途中位置の保存は設けない。

| 構成要素 | 責務 |
| --- | --- |
| 実行制御 | 入力順の処理、待機、スキップ・停止、終了結果の集計 |
| 設定・入力検証 | 設定読込、JSON全体と各要素の検証、対象選択 |
| ブラウザ取得 | Chrome接続、作業タブでの記事・画像取得、対象通信の照合 |
| 文書生成 | 本文抽出、Markdown変換、画像参照置換、メタデータ・ハッシュ生成 |
| 成果物保存 | 元URL照合、変更判定、一時保存からの反映、改名・破損修復 |
| 入力JSON更新 | 正常完了した要素の `is_new` の安全な書き戻し |
| 運用出力・排他 | ログ、件数表示、入力JSONと保存先の同時使用防止 |

実装はPython、ブラウザ接続はPlaywrightの同期APIとCDP、HTML変換はmarkdownify、exe化はPyInstallerのonefile方式とする。既存YAMLの読込はPyYAML、画像形式・デコード検証はPillowを用途を限定して使用する。JSON・TOML・ハッシュ・パス・待機は標準ライブラリで扱う。リポジトリ専用仮想環境を使用し、Pythonと依存の版は環境構築時に確認・固定する。

[PlaywrightのCDP接続](https://playwright.dev/python/docs/api/class-browsertype#browser-type-connect-over-cdp)には専用プロトコルより機能上の制限がある。[コンテキストのリクエストAPI](https://playwright.dev/python/docs/api/class-apirequestcontext)はCookieを共有し、画像取得の基本方式に使用する。変換・配布方式の根拠は[markdownify公式配布情報](https://pypi.org/project/markdownify/)と[PyInstallerの使用方法](https://pyinstaller.org/en/stable/usage.html)。公式資料確認日：2026-11-01。

配布対象はWindows 11向けexeと外部設定ファイル。Playwrightのドライバー等を同梱してPython未導入PCで確認する。ブラウザはユーザーのChromeを使い、Playwright用ブラウザの配布は前提にしない。Playwriterは限定調査用のツールであり、配布アプリの依存には追加しない。

## 3. 設定契約

exeと同じフォルダの `settings.toml` を起動時に一度読む。相対パスは設定ファイルの所在を基準とし、作業ディレクトリに依存させない。認証値は設定に格納しない。

| 項目 | 用途 | 既定・制約 |
| --- | --- | --- |
| `input.json_path` | 更新対象でもある入力JSONのファイルパス | 必須。原本とは別の既存の作業用コピー |
| `storage.output_dir` | Markdown・画像の保存ルート | 必須。フォルダを指定 |
| `logging.error_dir` | ログの保存先 | 必須。成果物と分離したフォルダ |
| `wait.interval_seconds` | 記事間の基準待機時間 | 180秒、0以上 |
| `wait.jitter_seconds` | 基準時間からのランダムな増減幅 | 10秒、0以上かつ基準以下 |
| `browser.connect_timeout_seconds` | Chrome接続の期限 | 設計初期値30秒、正の数 |
| `browser.page_timeout_seconds` | URL移動・記事API・本文描画・初回安定確認の共通期限 | 設計初期値60秒、正の数 |
| `browser.asset_timeout_seconds` | 画像1件の取得期限 | 設計初期値60秒、正の数 |

Chrome接続先は `http://127.0.0.1:9223` に固定する。タイムアウトの初期値は実装検証で妥当性を確認する。待機時間は基準±揺らぎの範囲で毎回抽選し、次の対象URLがない場合は記事間待機を行わない。

## 4. 入力JSONと連携契約

### 4.1 原本・作業用コピー

ユーザーがURL一覧作成アプリの出力JSONを別の場所へコピーし、コピー先を設定に指定する。コピー作成は事前準備とし、本アプリの自動機能には追加しない。再実行には同じコピーを使用する。

一覧作成アプリは原本のハッシュを管理するため、本アプリは原本と `run-state.json` を変更しない。コピーに `true` が残る間は次の一覧を生成・使用しない。取得を断念するURLは、ユーザーがログ確認後、実行停止中にコピーの値を手作業で `false` にする。正常完了または手作業による対象除外で `true` がなくなった後、原本を比較元として次の一覧を生成する。

`is_new: false` は、一覧作成時点で新規ではないURL、本アプリで正常完了したURL、手作業で除外したURLを含み、取得成功だけを保証する値ではない。

### 4.2 読込・検証・対象選択

| 対象 | 契約 |
| --- | --- |
| JSON全体 | UTF-8のJSONオブジェクトで、`urls` が配列であること。構文破損・重複キー・NaN等の非標準値は全体の読込失敗 |
| 配列要素 | オブジェクトで、空でない文字列 `url` とJSON真偽値 `is_new` を必須とする |
| 記事URL | HTTPS、ホスト `blackline.my.site.com`、パス `/BlackLineCommunity/s/article/` 配下、ユーザー情報・クエリ・フラグメントなし |
| 不正要素 | 配列内の位置と理由を記録し、失敗1件として値を修復せずスキップ |
| 取得対象 | 正常な `is_new: true` の要素を配列順に処理。正常な `false` は取得しない |
| 重複URL | 自動削除・並べ替えしない。各要素を入力順に処理し、通常の既存比較を行う |
| 保持対象 | URLの入力表記、未知の項目も含む各値、配列順。JSONの空白・インデントの維持は必須としない |

`schema_version`、`source_url`、`article_type`、`collected_at` は保持するが対象選択には使わず、これらだけの欠落で要素をスキップしない。構造の異なる将来版は契約を見直す。記事URLの検証と、8.1節の成果物同一性の正規化は用途を区別する。画像の配信先を記事と同じホストに限定するものではない。

## 5. 実行フロー・再実行

1. 設定・パスを検証し、11節の排他を確保する。
2. JSON全体を解析し、正常要素・不正要素を識別する。既存Markdownの元URL対応表を作る。
3. 対象があればChromeへ接続し、自分の作業タブでURLへ移動する。
4. 6節のAPI照合・本文完成判定後、7節の画像取得を行う。
5. 一時領域でMarkdownとメタデータを生成し、8節に従って比較・保存・必要な旧Markdown整理を行う。
6. 保存または無変更確認の正常完了後、9節に従い当該要素の `is_new` を `false` に書き戻す。
7. 失敗時は10節に従い、全体停止条件がなければ次の対象URLの前に規定待機する。成功後・スキップ後とも同じ待機を使う。
8. 一巡または全体停止時に、作業タブ・接続・排他を解放し、件数・終了結果を表示する。

取得失敗時のその場での再送・ページ再読込は行わない。中断後は、その時点で `true` のまま残った要素を先頭から処理する。JSON全体を読めない場合は取得せず異常終了する。対象0件かつ不正要素等の失敗がなければ処理件数0で正常終了する。

## 6. ブラウザ・記事取得契約

### 6.1 Chromeの使用と本文範囲

Chromeの起動とログインはユーザーが行う。既存のログイン済みコンテキストに作業タブを作り、既存タブを使い回さない。終了時は自分のタブだけを閉じ、Chrome全体・既存コンテキスト・ユーザーのタブは閉じない。

記事タイトルと記事内の全項目を保存し、ラベルと値を項目順に保持する。Question・Answerだけに固定しない。記事内部の `Related To` は本文項目として扱い、外部の関連記事一覧と混同しない。ナビゲーション・検索・評価欄は除外する。

限定調査では `.acknowltngKnowledgeArticleItem` 内の `h1.head-page__title` と `.acknowltngKnowledgeArticleBody` を一意に識別できた。変動する `data-aura-rendered-by` は固定セレクターに使わない。具体的な抽出・比較規則は、[調査記録](knowledge-article-observations.md)を根拠として詳細設計に固定する。

### 6.2 対象APIの照合

ブラウザが通常の画面遷移で発行するAura通信を観測し、内部APIを独自に再送しない。URL移動前から作業タブの監視を開始し、取得回ごとの識別子で前の記事と分離する。

| 処理 | 対象アクション | 対応付け |
| --- | --- | --- |
| 記事版ID解決 | `RecordServiceComponentController/ACTION$getArticleVersionId` | 要求 `urlName` と対象URL末尾、要求と応答のAuraアクションID |
| 記事情報 | `apex://acknowltng.KnowledgeArticleItemController/ACTION$getKnowledgeArticle` | 要求・応答の `articleId` と解決結果、応答の `title` と描画タイトル |
| 本文項目 | `apex://acknowltng.KnowledgeArticleBodyCtrl/ACTION$getFieldSetData` | 要求 `articleId`・`recordTypeName` と記事情報、要求と応答のAuraアクションID |

同じURLに複数のID解決応答があれば結果の一致を確認する。本文項目応答の `articleId`・`title`、記事情報の `urlName` が空となる正常例があるため、空値だけで不一致としない。非空の識別情報は矛盾がないことを確認する。

HTTP 200だけでは成功としない。1応答内の複数アクションを要求・応答IDで分け、対象アクションの成功を確認する。プロフィール・ナビゲーション・広告等の別通信や、ユーザーの別タブを判定に使わない。HTTPステータスが判明した対象通信には10.1節の優先順位を適用する。Cookie・トークン・要求本文全体をログや管理ファイルへ保存しない。

### 6.3 本文完成判定・期限

通常のQAフィールドセット表示では、次を満たしてから保存候補を確定する。

- 対象URLに留まり、記事コンポーネント・タイトル・本文が一意で可視である。
- ID解決・記事情報・本文項目が成功し、相互の対応が成立する。
- 項目順序・ラベル・値辞書と描画内容が対応する。値がない項目は必須にしない。APIに非空の値がある項目を、DOM未取得のまま省略して成功にしない。
- HTML・テキスト・画像参照のスナップショットが250ms間隔の連続2回で一致する。

URL移動から初回の安定確認までに共通の `page_timeout_seconds` を適用し、各待機で期限を加算し直さない。初期描画中の変化は期限内で安定を待つ。完成待ちは取得リトライと区別する。期限切れ・API不一致は記事をスキップする。

画像の遅延読込が必要な場合は作業タブの本文内で対象画像を表示位置へ移動し、ページ取得期限内で参照の確定を待つ。本文外のリンクを開いて画像を探さない。画像取得後にも候補のタイトル・本文・画像参照が変化していないことを確認し、変化していれば再取得せず失敗とする。

250msの一致は取りこぼしを減らす条件であり、将来の表示変更の保証ではない。APIとDOMの比較ではHTMLエンティティやラッパーの差を考慮し、具体的な正規化は詳細設計で検証する。空の非表示項目は保存しないが、非表示に実データがあるケースを未確認のまま成功扱いにしない。

## 7. 画像取得契約

本文画像の `currentSrc` を優先し、未設定の場合に `src` を用いる。相対参照は記事URLで解決する。本文外のロゴ・プロフィール・評価アイコンは対象にしない。

HTTP画像は既存コンテキストの `request.get` で取得する。Cookieを書き出したり別クライアントへコピーしたりしない。必要なURLクエリは取得時に保持するが、ログ・フロントマターには保存しない。

[GETオプション](https://playwright.dev/python/docs/api/class-apirequestcontext#api-request-context-get)で自動再試行・転送の自動追跡を無効にし、HTTPエラーも応答ステータスで判定する。転送応答は画像取得失敗として記事をスキップする。失敗時の別方式への自動切替・同じURLの再送は行わない。

各画像に `asset_timeout_seconds` を適用する。ブラウザの `complete` だけで成功とせず、読込状態・自然寸法と取得バイト列を検証する。実データの署名・デコード結果から形式と保存拡張子を決め、HTTPヘッダーの形式不一致だけでは失敗にしない。HTML・認識不能な内容・デコード不能な内容は画像として保存しない。

取得バイト列を一時領域で検証し、内容ハッシュを計算してから最終配置する。応答オブジェクトと不要なバイト列は解放する。画像1件でも失敗すれば、画像を欠いた記事を完成扱いにしない。data URI・blob URLのバイト列取得は詳細設計9節の方式で扱い、HTTP画像と同じ形式検証へ渡す。SVG等の未対応形式は黙って省略せず記事を失敗にする。特殊参照の確認範囲は[詳細設計検証記録](detailed-design-validation.md)を参照する。

## 8. 保存契約・更新・復旧

### 8.1 URL同一性・配置・ファイル名

記事の同一性は正規化した元URLで判定する。正規化はスキーム・ホストの小文字化とフラグメント除去のみで、パスの大文字小文字・クエリ・末尾スラッシュは保持する。別URLへの転送を同一記事として自動統合しない。

Markdownは保存ルート直下の `タイトル-元URLのSHA-256先頭8桁.md` とする。別URLとの衝突時は4桁ずつ最大64桁まで延長し、それでも別URLと衝突すれば異常終了する。元URL不明の破損ファイルとの衝突は8.5節の例外を適用する。長さの上限を超える場合はタイトル部分だけを短縮し、元タイトルとURLハッシュを維持する。短縮しても保存できない場合は記事単位の保存失敗とする。Windows禁止文字・予約名・末尾空白・長さ計算の具体的な処理は詳細設計5.2節に定める。

画像は `assets/<正規化した元URLのSHA-256全64桁>/<画像内容のSHA-256全64桁>.<形式の拡張子>` に保存し、同じ記事の同一画像をまとめる。本文からはMarkdown基準の相対パスで参照する。

### 8.2 Markdown・フロントマター

UTF-8・LFとし、先頭にYAMLフロントマターを置く。記事タイトルを最初のH1とし、本文に同一タイトルを重複追加しない。見出し・表・リンクを維持する。

| キー | 内容 |
| --- | --- |
| `title` | 元の記事タイトル |
| `source_url` | 元URL |
| `fetched_at` | 保存したデータの取得日時 |
| `created_at` | 本アプリでの初版作成日時。通常は更新・改名時にも引継ぎ |
| `updated_at` | 初回null、変更保存時は今回の保存日時 |
| `menu_path` | 記事タイトルだけの配列。メニュー階層は取得しない |
| `content_hash` | `sha256:<全64桁>` |
| `images` | `path`（保存ルート基準の相対パス）と `hash`（`sha256:<全64桁>`）の配列。画像なしは空配列 |

日時はタイムゾーン付きISO 8601形式とする。無変更時はMarkdown・画像を上書きせず、すべての日時を維持する。本文の画像参照と `images[].path` は基準を区別する。`attachments` は出力しない。

### 8.3 変更判定

内容ハッシュは `タイトル + LF + 本文Markdown` をUTF-8で符号化したSHA-256全64桁とし、タイトルのH1記号・フロントマターを含めない。画像参照は位置に依存しない画像ハッシュ識別子へ置換して計算する。改行をLF、全体末尾の改行を1つに統一し、本文中の空白を一律に削除・圧縮しない。

タイトル・内容ハッシュ・画像一覧と実バイト列を比較し、画像の追加・削除・差し替えも変更とする。日時だけでは変更としない。通常リンクの文字列・参照先の変更は本文変更に含めるが、リンク先のファイル内容は取得・比較しない。破損・重複は無変更扱いにせず8.5節で修復する。

### 8.4 保存・改名の順序

1. 同期対象外のローカル一時領域で取得・変換・検証を終える。
2. 元URLで既存記事を照合し、新規・更新・無変更を判定する。既存画像を再利用する場合も実バイト列のハッシュを確認する。
3. 新規・更新時は画像を先に最終配置する。
4. Markdownを最終保存先と同じファイルシステムの一時ファイルへ書き、書込完了後に置換する。既存Markdownへ直接書きかけの内容を保存しない。
5. 改名・重複の場合は新版を保存・検証してから、同一URLと確認できた旧Markdownを削除する。整理完了前にJSONを `false` にしない。
6. 正常完了後、9節のJSON書き戻しを行う。

複数ファイルとクラウド同期をまとめたトランザクションは保証しない。失敗時に反映済みファイルを一括ロールバックしない。不要な旧画像、元記事の削除・対象外化に伴う保存済み成果物は自動削除しない。

### 8.5 破損・重複・中断後の扱い

保存ルート直下のアプリ生成Markdownを `source_url` で対応付ける。画像配下・一時ファイルは記事として走査しない。ファイル名・タイトルだけで同じ記事と判断しない。

| 状態 | 処理 |
| --- | --- |
| 同一URLの重複 | 全体停止せず再取得し、現在タイトルの1ファイルへ保存後、同一URLと確認できた他のMarkdownを削除 |
| 元URLを読める破損 | 全体停止せず再取得して上書き。正常なメタデータは引継ぎ |
| 初版日時を復元不能 | 同一URLの候補に有効日時があれば最も早い日時を採用。なければ再生成日時を `created_at` とし、修復保存の `updated_at` も今回日時 |
| 元URLを読めない破損 | 当該ファイルを保持し、取得記事は別名保存。新しい記事の `created_at` は今回日時、`updated_at` はnull |
| 画像だけ反映済み | 再取得・通常比較を行い、既存画像を実ハッシュ検証後に再利用 |
| 画像の欠落・ハッシュ不一致 | 無変更にせず再取得・保存で修復。失敗時は未完了のまま維持 |
| Markdown保存済み・JSONは `true` | 再取得・比較し、正常完了後にJSONを書き戻す |
| 旧Markdown削除失敗 | 記事の保存失敗として `true` を保持。後続へ進み、再実行で修復 |
| 一時ファイル残存 | 完成成果物として扱わない。実行識別子付きの一時名を使用し、他の実行の残留物を無条件削除しない |

元URL不明ファイルと名前が衝突したら、URLハッシュを8桁から4桁ずつ延長する。全64桁でも占有されていれば、この場合に限り一意な接尾辞を付ける。次回は正常ファイルの `source_url` で照合し、毎回別名を増やさない。接尾辞の形式は詳細設計で固定する。

修復・対象不明ファイルの保持・初版日時の再設定は診断情報として記録する。元URL不明の保持ファイル自体を処理件数へ追加しない。修復処理の取得・保存・削除失敗は記事単位の失敗とし、全体停止条件がなければ後続へ進む。

## 9. 入力JSONへの完了記録

URL単位で、Markdown・画像・必要な旧Markdown整理の完了後に `is_new` を `false` にする。無変更確認も正常完了に含める。取得・比較・変換・保存に失敗した要素はアプリでは `true` のまま残す。

JSON全体を入力ファイルと同じフォルダの一時ファイルへUTF-8で保存し、再読込検証後に置換する。URL・未知項目を含む値・配列順を保持し、当該要素の `is_new` 以外を変更しない。URLごとの置換完了を待ち、一巡後へ保留しない。

書き戻し前に読込後の外部変更を確認し、検出時は上書きせずJSON更新失敗として停止する。外部編集との競合保証範囲は11節の排他と合わせ詳細設計で定める。更新失敗時も保存済み成果物・先行要素の完了記録を保持する。

## 10. 異常時動作・集計・ログ

### 10.1 スキップと全体停止

| 事象 | 処理 |
| --- | --- |
| 対象記事・画像通信の401～409 | 記事をスキップ。同じ記事でログイン画面も検出した場合もスキップを優先 |
| 対象通信の400・410～499 | 全体を異常終了 |
| 上記スキップ応答がなく、ログイン切れを確認 | 全体を異常終了。自動ログインしない |
| 不正要素、その他の取得・比較・変換・保存失敗 | 当該要素を失敗として記録し、次の対象URLの前に規定待機して続行 |
| JSON全体を読めない | 取得開始前に異常終了 |
| JSON書き戻し失敗 | 全体を異常終了し、保存済み成果物を保持 |
| 指定先へのログ保存失敗 | 10.3節の代替出力・表示を試みて全体を異常終了 |

ログイン切れは単なる本文表示失敗だけで推測しない。具体的な画面・転送先の識別条件は観測または匿名化資料を根拠に詳細設計で固定する。ログアウトやCookie削除による実アカウントの破壊的な調査は行っていない。

スキップ・記事失敗があれば一巡後に終了コード1、全体停止も1とする。失敗なしで一巡完了または正常0件なら0とする。手動中断・後片付け失敗も1とし、後続URLを開始せず、可能な残りの終了処理を試みる。保存済み成果物と完了記録は維持する。

### 10.2 件数

集計単位は入力配列の各要素とし、重複URLも要素ごとに数える。次の4分類は重複させない。

| 表示分類 | 条件 |
| --- | --- |
| 新規保存 | 既存記事がなく、成果物保存とJSON書き戻しが成功 |
| 更新 | 既存記事の変更・修復・重複整理とJSON書き戻しが成功 |
| 変更なし | 取得・比較で無変更を確認し、JSON書き戻しが成功 |
| 失敗 | 不正要素、取得・比較・変換・保存失敗、当該要素のJSON書き戻し失敗 |

正常な `false` と停止後の未着手要素は数えない。対象要素を特定できない設定不備・JSON全体破損等は実行全体のエラーとして表示し、URL失敗件数へ架空の1件を加えない。4分類がすべて0でも異常終了する場合がある。

成果物保存後にJSON更新が失敗した要素は失敗1件とし、成功へ二重計上しない。成果物反映済み・完了記録未反映の段階をログに残す。既に正常完了した先行要素の件数は維持する。強制終了・PC停止時の最終表示は保証しない。

### 10.3 ログ契約

エラー1件につきUTF-8のJSONを1ファイル作る。日時・実行識別子・一意な接尾辞で命名し、既存ログを上書きしない。項目は `occurred_at`、`run_id`、`input_index`、`source_url`、`stage`、`error_code`、`http_status`、固定文の `message` とし、不明値はnullとする。

Cookie・認証ヘッダー・トークン・本文・生の例外文字列を保存しない。URLは秘密値を除いた識別情報にする。指定先に保存できなければ、同期対象外の `%LOCALAPPDATA%/BlackLineKnowledgeCrawler/fallback-errors/` への代替保存と標準エラー表示を試み、代替の成否にかかわらず全体を異常終了する。すべてのファイル出力が失敗した場合は、画面で記録不能と停止理由を示す。失敗通知が再帰的にログを生成しないようにする。

ログ障害で保存済みファイルを削除したり、書き戻し済みの `false` を `true` に戻したりしない。

## 11. 排他・パスの同一性

同一PCでは入力JSONと保存ルートに対応する別のロックファイルを用い、実行中はOSの排他ロックを保持する。置換されるJSON本体だけをロック対象にせず、ロックファイルの存在だけで起動可否を判断しない。プロセス終了時にOSがロックを解放する方式とする。

- 同じJSONなら保存先が違っても、同じ保存先ならJSONが違っても同時実行しない。
- 取得順を固定してすべてのロックを確保し、確保できなければ巡回開始を待機せず起動エラーとする。
- 絶対パス化、既存親の解決、大文字小文字・別名・リンクによる同一実体の判定方法は詳細設計で定める。
- 入力の手作業編集は停止中に行う。ロックを尊重しない外部編集には書き戻し前の変更検出も併用するが、完全な競合防止を保証しない。
- ローカルロックはOneDrive等を通じ別PCへ共有されない。同じ同期先・作業用JSONを別PCから同時変更しないことは利用者の運用制約とし、分散ロックは追加しない。
