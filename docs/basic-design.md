状態：基本設計初稿。要件定義で合意した保存仕様に、構成・設定・処理フロー・検証方針を追加した。未解決事項は12節に集約する。

## 1. Markdownの保存契約

[要件定義書](requirements.md) FR-08に基づき、参考アプリの[設計書7節・15.1節・15.2節](references/bl-documents-crawler/docs/design.md)のMarkdownファイル仕様を採用する。ただし、FR-09により階層別フォルダは使用せず、FR-10により添付ファイルの保存を追加する。

- UTF-8・LFで保存し、先頭にYAMLフロントマターを置く。記事タイトルを先頭のH1とし、本文の同一タイトルを重複させない。見出し・表・リンクを維持し、サイト共通のヘッダー・メニュー・検索欄は本文から除外する。
- ファイル名は `タイトル-元URLのSHA-256ハッシュ先頭8桁.md`。別URLとの衝突時は4桁ずつ最大64桁まで延長し、それでも衝突する場合は異常終了する。
- URLの正規化はスキーム・ホストの小文字化とフラグメント除去に限定する。パスの大文字小文字・クエリ・末尾スラッシュは保持する。
- フロントマターのキーは `title`、`source_url`、`fetched_at`、`created_at`、`updated_at`、`menu_path`、`content_hash`、`images` とする。`images` の各要素は `path` と `hash` を持ち、画像がなければ空配列とする。
- 日時はタイムゾーン付きISO 8601形式。`created_at` は本アプリでの初版作成日時を保持する。`updated_at` は初回はnull、変更保存時は保存日時とする。`fetched_at` は保存データの取得日時で、無変更時には既存値を維持する。
- 記事Markdownは保存ルート直下に配置し、メニュー階層でフォルダを分けない。`menu_path` は記事タイトルだけの配列（例：`["記事タイトル"]`）とし、メニュー階層は取得しない。
- 画像は保存ルートの `assets/<正規化した元URLのSHA-256全64桁>/` に、画像バイト列のSHA-256全64桁と種類に対応する拡張子で保存する。同じ記事の同一画像はまとめる。
- 本文の画像参照はMarkdownからの相対パス、`images[].path` は保存ルートからの相対パスとする。`images[].hash` は `sha256:<全64桁>` とする。
- `content_hash` は `sha256:<全64桁>`。計算対象は `タイトル + LF + 本文Markdown` のUTF-8表現とし、タイトルのH1記号とフロントマターを除く。画像参照は位置に依存しない画像ハッシュ識別子へ置換し、改行をLF、全体末尾の改行を1つに統一する。本文中の空白は一律に削除・圧縮しない。

## 2. 添付ファイルの保存

- 記事に添付されたファイルを元の形式でローカル保存する。
- 記事の添付欄と本文内のダウンロードリンクを対象とし、通常のWebページへのリンク先は取得しない。
- Markdown内の添付ファイルへのリンクは、Markdown所在を基準としたローカルの相対パスに置換する。
- 配置・命名・衝突回避・メタデータの詳細は今後の設計で定める。

## 3. 再実行と更新

- 入力JSONの `is_new: true` のURLを再取得し、正規化した元URLで保存済み記事と対応付ける。
- タイトル・本文・画像・添付ファイルに変更がある場合だけ既存ファイルを更新する。画像・添付ファイルの追加・削除・差し替えも変更として扱う。
- 無変更時には既存Markdownと保存済み画像・添付ファイルを上書きせず、フロントマターの日時も維持する。
- 更新時は `created_at` を引き継ぎ、`updated_at` に今回の保存日時を記録する。

## 4. 入力・保存先の指定と実行単位

- 入力JSONのファイルパスと保存先フォルダは外部設定ファイルで指定する。設定ファイルの形式・名前・項目名は今後の設計で定める。
- 取得対象URLは入力JSONに記載された順に処理する。
- 取得失敗時はその場で再試行せず、次回起動時に `is_new: true` のまま残っているURLを再処理する。
- URL一覧の各要素に必須項目の欠落や型の不正などがある場合は、当該要素をスキップして次のURLへ進む。不正要素は失敗件数に含め、ログに記録し、残りの対象を処理した後に異常終了する。全体停止条件を検出した場合はその時点で停止する。
- JSON全体の構文破損や `urls` 配列の欠落・型不正などによりURL一覧を読み取れない場合は、取得を開始せず、エラーを記録して異常終了する。
- 1回の実行で `is_new: true` の対象URLを一巡して終了し、自動的な繰り返し巡回は行わない。
- 途中位置を保持する再開機能は設けず、再実行時点で `is_new: true` のまま残っているURLを先頭から処理する。
- JSONは入力と処理状態の更新先を兼ねる。URLごとにMarkdown・画像・添付ファイルの保存完了後、該当URLの `is_new` を `false` に書き戻す。一巡後まで書き戻しを保留しない。
- 書き戻しでは正常完了したURLの `is_new` だけを変更し、URL・配列の並び順・その他の項目と値を保持する。
- 再取得して変更なしと確認できた場合も正常完了として `false` にする。取得・保存失敗時には `true` のまま残す。
- JSONへの書き戻しに失敗した場合は、エラーを記録して全体を停止する。保存済みファイルは保持する。
- 入力JSONが読み取れ、入力不正などの失敗がなく、取得対象URLが0件の場合は処理件数0で正常終了する。不正要素がある場合は失敗として扱う。
- 一巡中に取得・変換・保存の失敗があった場合は残りの対象URLを処理したうえで異常終了する。ログイン切れ、JSONへの書き戻し失敗、HTTP 400および410～499による全体停止を優先する。
- 記事の処理完了後、次の記事へ進むまで基準待機時間にランダムな揺らぎを加えて待機する。既定値は基準180秒、揺らぎ±10秒とし、両方を外部設定ファイルで秒単位に変更可能とする。
- 取得に失敗して次の記事へ進む場合も、同じ基準待機時間とランダムな揺らぎを適用する。
- 記事・画像・添付ファイルの取得でHTTP 401～409となった場合は当該記事をスキップし、エラーを記録して規定待機後に次の対象URLへ進む。記事の更新を見送り、`is_new` は `true` のまま保持する。これらの応答だけではログイン切れとして全体停止しない。一巡後は取得失敗ありとして異常終了する。
- HTTP 401～409以外の4xx（400および410～499）の場合は、当該記事の更新を見送り、`is_new` は `true` のまま保持する。エラーを記録して全体を異常終了し、次の対象URLへ進まない。

## 5. 取得範囲と同時実行

- 記事タイトルと記事内の全項目（質問・回答など）を保存し、ナビゲーション・関連記事・評価欄などは除外する。
- 同じ入力JSONまたは同じ保存先を使用する複数プロセスの同時実行を禁止する。防止方式は今後の設計で定める。

### 合意済みの補足方針

- 現在の入力JSONに `is_new: true` が残っている間は、次のURL一覧を生成・使用しない。取得を断念するURLはユーザーがログを確認し、手作業で `false` に変更して対象から外す。アプリは失敗URLを自動で `false` にしない。正常完了または手作業による対象除外で `true` がなくなった後、次のURL一覧を生成・使用する。
- 同じ記事の取得でHTTP 401～409とログイン画面の両方を検出した場合もスキップを優先する。これらの応答がない場合に、別の方法で確認したログイン切れによる全体停止を適用する。
- Markdown変換・ローカル保存失敗は記事単位で記録してスキップし、規定待機後に続行して一巡後に異常終了する。入力JSONへの書き戻し失敗は即時停止し、保存済みファイルを保持する。

## 7. 全体構成

1プロセスでURLを逐次処理する。並列取得・DB・定期実行基盤は設けない。Windows 11向けexeと外部設定ファイルを配布し、Chromeの起動とログインはユーザーが行う。

| 構成要素 | 責務 |
| --- | --- |
| 実行制御 | 入力順の処理、待機、スキップ・停止、終了結果の集計 |
| 設定・入力検証 | 設定読込、JSON全体と各要素の検証、対象選択 |
| ブラウザ取得 | ポート9223への接続、作業タブでの記事・画像・添付取得、対象通信の判定 |
| 文書生成 | 本文抽出、Markdown変換、ローカル参照への置換、メタデータとハッシュ生成 |
| 成果物保存 | 元URLでの照合、変更判定、一時保存からの反映、既存ファイル管理 |
| 入力JSON更新 | 正常完了した要素の `is_new` の更新と安全な書き戻し |
| 運用出力・排他 | ログ、件数表示、入力JSONと保存先の同時使用防止 |

参考クローラーのPythonによる逐次処理と責務分割を基本方針とする。採用ライブラリ・版・ビルド方式はAPIと配布条件を確認して本書で確定し、依存一覧へ固定する。現時点では環境構築や依存追加は行わない。

## 8. 設定・入力契約

### 8.1 外部設定

設定ファイル名を `settings.toml` とし、exeと同じフォルダから読む。相対パスは設定ファイルの所在を基準とし、作業ディレクトリに依存させない。起動時に一度読み、認証値を格納しない。

| 項目案 | 用途 | 既定・制約 |
| --- | --- | --- |
| `input.json_path` | 更新対象でもある入力JSONのファイルパス | 必須。原本とは別の既存の作業用コピーを指定 |
| `storage.output_dir` | Markdown・画像・添付の保存ルート | 必須。フォルダを指定 |
| `logging.error_dir` | エラーログの保存先フォルダ | 必須。成果物と分離 |
| `wait.interval_seconds` | 記事間の基準待機時間 | 180秒、0以上 |
| `wait.jitter_seconds` | 基準時間からのランダムな増減幅 | 10秒、0以上かつ基準以下 |
| `browser.connect_timeout_seconds` | Chrome接続の期限 | 初期案30秒、正の数 |
| `browser.page_timeout_seconds` | 記事表示・本文取得の期限 | 初期案60秒、正の数 |
| `browser.asset_timeout_seconds` | 画像・添付1件の取得期限 | 初期案60秒、正の数 |

Chromeの接続先は `http://127.0.0.1:9223` とし、要件の固定ポートを設定で変更しない。待機時間は基準±揺らぎの範囲で待機ごとに抽選する。次の対象URLがない場合は記事間待機を行わない。タイムアウト値はサイト調査時に妥当性を確認する。

### 8.2 JSONの読込と保持

- ユーザーがURL一覧作成アプリの出力JSONを別の場所へコピーし、その作業用コピーを `input.json_path` に指定する。コピー作成は利用者の事前準備とし、本アプリの自動機能には追加しない。再実行には同じコピーを使用する。
- 原本と一覧作成アプリの `run-state.json` は変更しない。次回の一覧生成は原本を比較元とし、現在の作業用コピーに `true` が残っていないことを利用者が確認してから実行する。
- 入力はURL一覧作成アプリのUTF-8 JSONを使用する。`urls` 配列内の正常な要素は、空でない文字列 `url` とJSON真偽値 `is_new` を持つ。
- JSONを解析できない、最上位がオブジェクトでない、`urls` が配列でない場合は取得開始前に異常終了する。
- 不正要素は配列内の位置と理由をログに記録し、1要素を失敗1件として保持したままスキップする。値を推測して補完・修復しない。
- `is_new: false` の正常要素は取得しない。`true` の正常要素は配列順に処理する。
- 元URLは入力の表記を保持する。成果物の同一性・命名には1節の正規化を使用する。
- 未知の項目も含めJSONの値と配列順を保持し、正常完了した要素の `is_new` だけを変更する。空白・インデントなどのテキスト表現の維持は必須としない。
- URLの許容形式、重複URL、トップレベルの版・固定値の検証方針は12節で継続検討する。

## 9. 実行フローとブラウザの使用

1. 設定を読み、入力・保存先・ログ先のパスを検証する。
2. 入力JSONと保存先の排他を確保する。WindowsのOS管理のファイルロックを用い、終了時に解放する。ロック識別・取得順・OneDrive等での適用範囲は詳細設計で定める。
3. 入力JSONを解析し、正常要素と不正要素を識別する。保存済みMarkdownを元URLで照合できるよう確認する。
4. 取得対象があればChromeへ接続し、ユーザーの既存タブと分離した作業タブで対象URLを開く。既存タブやChrome全体は閉じない。
5. 記事のタイトル・本文全項目と、画像・添付を取得する。ログイン画面やエラーHTMLを記事・画像・添付として保存しない。
6. 一時領域でMarkdown・資産・ハッシュを生成して既存内容と比較し、新規保存・更新・変更なしを判定する。
7. 保存または変更なし確認が成功した要素だけ、入力JSONの `is_new` を `false` に書き戻す。
8. スキップ時は失敗を記録し、入力の状態を維持する。全体停止条件がなければ、次の対象URLの前に規定待機する。その場で再取得しない。
9. 終了時に作業タブ・接続・排他を解放し、件数と終了結果を表示する。

記事・画像・添付に関係する通信だけを判定し、広告・計測など無関係な通信の4xxで記事を停止・スキップしない。通信と対象記事との対応方法、本文の完成判定、遅延読み込み・ダウンロード・転送の観測条件は、実際の構造確認後に確定する。

| 事象 | 基本動作 |
| --- | --- |
| 対象通信の401～409 | 記事をスキップ。ログイン画面も検出した場合も同じ |
| 対象通信の400・410～499 | 全体を異常終了 |
| 上記スキップ応答がなくログイン切れを確認 | 全体を異常終了、自動ログインしない |
| その他の取得失敗、変換失敗、成果物保存失敗 | 記事をスキップし、待機後に次へ |
| 入力JSONの更新失敗 | 保存済み成果物を保持して全体を異常終了 |

## 10. 保存・変更判定・JSON書き戻し

### 10.1 添付の配置案

画像と混同しないよう、添付は `attachments/<元URLのSHA-256全64桁>/` 配下とする。内容バイト列のハッシュで同名ファイルの衝突を避け、元の形式を維持する。元ファイル名・本文のリンク文字列・保存パス・内容ハッシュを対応付ける。命名とメタデータ項目は、参考仕様のフロントマターに追加する契約として設計レビューで確定する。

### 10.2 変更判定と反映

- 元URLで同じ記事を特定し、タイトル・本文・画像一覧とバイト列・添付一覧とバイト列を比較する。日時だけでは変更としない。
- 無変更時は既存成果物と日時を維持する。タイトル変更時も同じURLの初版作成日時を引き継ぐ。
- 同期対象外のローカル一時領域で生成と取得を完了してから、資産、Markdownの順に最終反映する。既存Markdownへ直接書きかけの内容を保存しない。
- 最終保存先と同じファイルシステムに一時ファイルを置き、書込完了後に置換する。複数ファイルとクラウド同期をまとめたトランザクションは保証しない。
- 途中失敗時は `is_new` を変更しない。途中反映済みの資産、改名途中、管理ファイル破損などの検出と復旧方針は12節で定める。

### 10.3 入力JSONの更新

正常完了した要素の `is_new` を変更したJSONを、入力JSONと同じフォルダの一時ファイルへUTF-8で保存し、再読込検証後に置換する。変更前の入力JSONへ直接書き込まない。URLごとに置換を完了してから次へ進む。

読込後に別プロセス・手作業で入力が変更されていないことを、書き戻し直前に確認する。変化を検出した場合は上書きせずJSON更新失敗として停止する。外部編集との競合保証範囲は排他方式と合わせ詳細設計で定める。

成果物保存後・JSON更新前の中断では、成果物が存在しても `true` が残る。再実行時は再取得・比較し、変更なしを確認してから `false` にする。

## 11. ログ・終了・検証と配布確認

- 新規保存・更新・変更なし・失敗を表示する。入力JSON更新失敗時など、成果物の状態と完了記録が食い違う場合の件数定義は設計レビューで固定する。
- エラーログは実行単位で分離し、日時・入力要素の位置・処理段階・理由・HTTPステータスを記録する。Cookie・認証ヘッダー・トークン・ページ本文を記録しない。URLは秘密値を除いた識別情報とする。
- 正常終了は終了コード0、失敗ありまたは全体停止は終了コード1を基本とする。手動中断の終了コードは詳細設計で定める。
- 保存ルートに記事Markdownと資産、ログ先に運用出力を置く。参考アプリ固有の監視用完了日時ファイルは、今回の要件へ自動追加しない。

| 検証対象 | 確認内容 |
| --- | --- |
| 入力・設定 | 真偽値の厳密判定、不正要素と全体破損、空配列、未知項目と順序保持、パス基準 |
| 取得 | ダミー画面で本文境界、画像・添付、ログイン画面、対象通信と無関係な通信を分離 |
| エラー制御 | 401～409、400・410～499、その他取得失敗、変換・保存失敗、ログイン切れの優先順位 |
| 保存・更新 | 新規・無変更・本文更新・画像更新・添付更新、元URL照合、日時維持、ファイル名衝突 |
| 完了記録 | URLごとの書き戻し、JSON更新失敗、外部変更検出、保存後・JSON更新前の中断 |
| 実行 | 入力順、一巡終了、待機と揺らぎ、スキップ後の待機、同時実行防止、件数・終了コード |
| 配布 | 日時等で一意な `dist/` 配下へのexe出力、旧exe保持、Python未導入Windows 11での起動、作業ディレクトリ非依存 |

通常の検証はモック・ダミー資料で行う。実サイトの読取確認は対象・保存場所を明確にして別途実施し、既に実施済みとは扱わない。PROD更新リクエストによるテストは行わない。
