# 要件定義書 — BlackLine Knowledge URL一覧作成アプリ

作成日：2026-10-29
状態：要件定義レビュー完了。2026-11-01までの追加合意を本文へ統合済み。設計への対応は5節に記載する。

## 1. 目的

BlackLineというSaaS製品のKnowledge文書を保存するため、文書のURL一覧を取得し、別アプリが読み取るファイルとして保存する。

本アプリの責任範囲はURL一覧の作成までとする。各URLのページを取得してMarkdownで保存する処理は、別アプリが担当する。

## 2. 利用の前提

- Knowledgeはログインが必要なウェブサイトである。
- 本アプリはログイン済みChromeのセッションを利用してスクレイピングする。
- Chromeへの接続先は `127.0.0.1:9223` を想定する。
- Knowledge一覧の起点URLは `https://blackline.my.site.com/BlackLineCommunity/s/knowledge` とする。
- 別アプリが、本アプリの保存したURL一覧を読み取り、対象ページをクロールする。

対象OSはWindows 11とし、Pythonのインストールを必要としないexeと外部設定ファイルを配布する。実行前にユーザーがChromeでログインを済ませ、Chromeを起動したまま本アプリを実行する。利用者はユーザー本人と同じ会社のチームメンバーとする。Chromeの具体的な起動手順と接続先を変更可能にするかは基本設計で定める。

開発・テスト・ビルドには本リポジトリ専用のPython仮想環境を使い、Python版は環境構築時の最新安定版を採用・固定する。配布先にPython導入を要求しない方針は維持する。

## 3. 責任範囲

### 3.1 対象

1. ログイン済みChromeのセッションを利用する。
2. Knowledgeページで記事種別（ARTICLE TYPE）「QA」のチェックボックスを選択して表示される記事一覧から、記事リンクを取得する。
3. ページネーションを先頭から1回走査し、最終ページまたは1,000件到達までの記事リンクを取得する。
4. URL一覧を、別アプリが読み取れるファイルとして保存する。

収集条件は4節、保存情報は4.1節に定める。左メニューツリー全体や本文中リンクの探索は対象に含めない。

### 3.2 対象外

- 収集した各URLをクロールし、本文をMarkdownに変換・保存する処理。
- 文書に含まれる画像や添付ファイルを成果物として保存する処理。
- 別アプリによるクロールの実行と、その保存結果の管理。

一覧のフィルター操作とページネーションは収集対象に含む。記事URLは一覧のタイトルリンクから取得し、各記事ページを開く処理は行わない。

## 4. 確定した機能要件

| ID | 要件 |
| --- | --- |
| FR-01 | Knowledgeへのアクセスには、2節のログイン済みChromeのセッションを利用する。 |
| FR-02 | Chromeへの接続先は2節に定める。 |
| FR-03 | Knowledgeページで記事種別（ARTICLE TYPE）「QA」を選択した記事一覧から、記事URLを取得する。 |
| FR-04 | 取得したURL一覧をファイルとして保存する。 |
| FR-05 | 保存したURL一覧を別アプリが読み取れるよう、出力仕様を定める。形式・項目は4.1節に定める。 |
| FR-06 | QA記事一覧を先頭から1回走査し、最終ページまたは1,000件到達までの記事リンクを取得する。1,000件は重複排除前の収集件数とし、累積JSONの件数には適用しない。 |
| FR-07 | 取得処理中に、提示されたアンケートモーダル（画面は参照資料を参照）が表示された場合は下部の「Close」を押して閉じ、一覧取得を続行する。表示されない場合も取得を継続する。回答入力・送信は行わない。閉じられず取得を継続できない場合は異常終了する。他の種類のモーダルを同じものと推測して閉じない。 |
| FR-08 | 2節のKnowledge一覧URLを起点とする。 |
| FR-09 | QA記事は英語・日本語・その他の言語を含め、言語による除外を行わず記事URLを取得する。 |
| FR-10 | 毎回QA一覧から最大1,000件のURLを取得し、前回JSONの全URLを保持した累積一覧をJSONに保存する。2回目以降は前回JSONと比較し、各URLに新規／取得済みの区分を記録する。今回一覧から外れた保存済みURLも削除しない。 |
| FR-11 | 各実行のJSONは実行年月日・時刻（秒まで）で命名した別々のディレクトリに保存し、過去の出力を上書きしない。 |
| FR-12 | 同じ秒の同時起動を禁止する制御は設けない。出力ディレクトリ名が重複した場合は、既存の内容を変更せずアプリを終了する。 |
| FR-13 | 初回はすべてのURLを新規とする。2回目以降は前回JSONに同じURLが存在すれば取得済み、存在しなければ新規とする。前回の新規／取得済みの区分は判定に使わない。 |
| FR-14 | 途中再開機能は設けない。失敗・中断後の再実行では最初のページから取得する。 |
| FR-15 | 同じ保存先の前回成果物の正常完了と比較元JSONの健全性など継続条件を満たす場合だけ継続する。公開前の失敗・中断、JSONの破損・欠落、成果物の完了を確認できない場合は異常終了する。公開後の後始末だけの失敗は4.2節に従い、成果物を未完了とはしない。古いJSONへの自動切替は行わず、履歴がまったくない場合だけ初回とする。 |

### 4.1 出力形式（採用済み）

別アプリへの受け渡し形式はUTF-8のJSONとする。

保存する情報は、ファイル仕様の版、取得元の一覧URL、選択した記事種別、今回の取得完了日時、累積の記事URLと各URLの新規／取得済みの区分とする。取得完了日時にはタイムゾーンを含める。

具体的なJSONのキー名・型・形式・新規判定規則は [基本設計書3節](basic-design.md#3-json保存契約) に集約する。

同一URLは重複排除する。一度正常保存したURLは将来の一覧から外れても以後のJSONに保持する。1,000件は1回の収集上限であり、累積JSONの件数には適用しない。格納順とURLの同一性の判定規則は基本設計で具体化する。タイトル・階層・記事IDは出力項目に含めない。

完成JSONの保存条件と異常時の扱いは4.2節に定める。

### 4.2 実行・保存・異常時の要件（採用済み）

- ARTICLE TYPEはQAのみを選択し、CATEGORYなど他の絞り込み条件は解除する。
- 1回の起動でFR-06の収集範囲を取得・累積保存して終了する。実行中の操作を必要としないバッチ形式とする。ただし、実行前のChrome起動・ログインはユーザーが行う。
- 保存先の親ディレクトリは `settings.toml` で指定する。実行ごとの保存と取得区分はFR-10・FR-11・FR-13に従う。
- 実行日時には、アプリ実行開始時のPCのローカル日時を使用する。
- 初回は前回比較を行わず、FR-06の収集範囲の取得・完全性確認に成功した場合に完成JSONを保存する。2回目以降は前回比較・累積統合にも成功した場合だけ保存する。ページ抜け・意図しない重複遷移がなく、正常な収集終端に到達したことを確認する。同一記事URLの重複排除とは区別する。途中失敗の部分一覧は完成JSONとして保存しない。
- Chrome接続不可、ログイン切れ、ページ取得失敗など、取得を完了できない場合はエラーをファイルへ記録して異常終了する。不完全な一覧で既存の完成ファイルを上書きしない。
- ログイン切れの場合は自動ログインを行わず停止する。ユーザーがChromeで再ログインした後に再実行する。
- 再実行と前回比較はFR-14・FR-15に従う。失敗・中断後はユーザーが保存ディレクトリを手作業で整理し、継続条件を満たした状態で再実行する。
- 継続条件を満たさない場合のログには、停止理由と確認対象の保存ディレクトリを記録し、「保存されたJSONのディレクトリを確認し、手作業で整理してから再実行してください」と利用者に分かるよう案内する。アプリが履歴の自動修復・削除を行うことはない。
- 取得途中の件数変化、ページ番号の不連続、応答と画面の不一致などを検出した場合は完成扱いにせず異常終了する。1回走査を採用し、件数不変の入れ替わりなどを検出できない限界を受け入れる。具体的な検出対象と限界は基本設計書8.3節に定める。
- QAのみ・CATEGORYなしの条件で件数APIと記事一覧がともに正常に0件を返した場合は正常終了し、前回URLを全件取得済みとして保持する。初回は空のURL配列を保存する。通信失敗・条件不一致・件数と一覧の不一致を正常0件と扱わない。
- 対象一覧の通信失敗は異常終了1とし、今回の完成JSONを公開しない。完成JSON公開後の作業タブ閉鎖・切断だけの失敗も終了1とするが、公開済み成果物は正常完了のまま保持する。

### 4.3 出力ファイル名（採用済み）

各実行ディレクトリ内の完成ファイル名は `knowledge-qa-urls.json` とする。実行ごとにディレクトリが異なるため、ファイル名自体には日時を付けない。ディレクトリの命名と重複時の処理は `docs/basic-design.md` に定める。

## 6. 受入条件

以下を受入条件とする。実行可能な確認手順と具体的なテストデータは設計段階で定める。

- ログイン済みChromeのセッションを想定接続先から利用できる。
- QAのチェックボックスによる絞り込み後、FR-06の収集範囲のリンクを取得できる。
- 指定のKnowledge一覧URLを起点とし、QA記事を言語によって除外せずにURL一覧へ含める。
- 合意したファイル仕様で一覧を保存でき、別アプリが読み取れる。
- UTF-8のJSONに4.1節の項目を記録し、同一URLを1オブジェクトずつ、基本設計3節の順序で保存する。
- 毎回の収集結果と保存済みURLを累積統合し、実行日時別ディレクトリ内の `knowledge-qa-urls.json` に保存する。今回一覧から外れたURLを保持し、累積1,000件超を許可する。
- 初回は全件が新規となる。2回目以降は前回JSON内の同一URLの有無だけで区分し、前回の区分の値は判定に影響しない。
- 前回成果物の正常完了と比較元JSONの健全性など継続条件を満たさない場合、古いJSONへ自動切替せず異常終了し、停止理由・対象ディレクトリ・手動整理を促すログを出力する。履歴がまったくない場合だけ初回となる。
- 失敗・中断後に再実行すると、途中のページから再開せず最初のページから取得する。
- 出力ディレクトリ名が重複した場合は既存内容を変更せず終了し、同じ秒の同時起動を禁止する制御を設けない。
- QA以外の絞り込みを解除したうえで収集し、1回の起動で保存して終了する。
- 取得失敗・ログイン切れ・一覧の途中変化の検出時は、エラーを記録して異常終了し、既存の完成ファイルを維持する。
- Windows 11でPythonを別途インストールせずにexeを実行でき、`settings.toml` で保存先を指定できる。
- 本アプリの成果物として、ページ本文のMarkdownや画像を保存しない。
- 提示されたアンケートモーダルが表示された場合は「Close」で閉じて取得を続行でき、表示されない場合も取得できる。回答の入力・送信を行わない。
- 正常0件と通信失敗を区別し、正常0件では前回URL保持、通信失敗では今回の公開抑止を確認する。公開後の後始末失敗では成果物保持と終了1を確認する。

実際の0件表示の再現と不定期アンケートの出現待ちは設計確定の条件としない。これらの分岐はダミー画面・モック応答で検証する。実サイト調査済みの範囲と未確認事項は観察記録を参照する。

## 7. 文書と参考資料の関係

- 本書を本アプリの要件定義の正本とする。未決事項は確定要件として扱わない。
- 基本設計は `docs/basic-design.md`、詳細設計は `docs/detailed-design.md` に分けて作成する。
- `docs/references/design.md` には本文・画像の保存、Markdown化、連続巡回などの記載があり、今回指定された責任範囲とは異なる。本書への自動的な引き継ぎは行わない。
- ユーザーの回答に基づき同資料は参考にするが、採用する要件は個別に確認する。その後の推奨案の一括採用により、Windows 11・exe配布・外部設定ファイル・バッチ実行は採用済みとする。その他の要件は自動的に引き継がない。
- 参考資料内の過去の合意・検証結果を、本アプリの合意・検証済み事項とは扱わない。参照先が不足する場合も推測で補完しない。
