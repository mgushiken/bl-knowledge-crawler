## 1. 根拠と対象

要件の正本は[要件定義書](requirements.md)とする。本書は動作仕様・外部入出力・保存契約・構成・技術選定を定める。モジュール・関数・内部状態形式・アルゴリズム・具体的なセレクターは[詳細設計書](detailed-design.md)に記載する。実測経緯は[観察記録](references/knowledge-ui-observations.md)を参照し、仕様本文へ調査時点の未確定案を重ねて管理しない。

## 2. 出力ディレクトリ

- `settings.toml` で指定する保存先を親ディレクトリとし、その直下に実行年月日・時刻を秒まで含めたディレクトリを作成する。
- 各実行ディレクトリ内の出力ファイル名は `knowledge-qa-urls.json` とする。
- JSONの保存内容と前回比較は3節に定める。
- 過去の実行ディレクトリとJSONは上書きしない。
- 手動実行を前提とし、同じ秒の同時起動を禁止する制御は追加しない。
- 作成対象の実行ディレクトリ名が既に存在する場合は、そのディレクトリを再利用せず、既存内容を変更せずに終了する。時刻をずらした再試行や連番の付与も行わない。

### 2.1 実行日時

日時はアプリ実行開始時のPCのローカル日時を使用する。

ディレクトリ名は `YYYYMMDD_HHMMSS` とする。Windowsのディレクトリ名として使用でき、名前順で開始日時順に並ぶ。例えば2026年10月29日14時05分09秒の実行は、以下の配置となる。

```text
<settings.tomlで指定した保存先>/
  20261029_140509/
    knowledge-qa-urls.json
```

## 3. JSON保存契約

出力はUTF-8のJSONオブジェクトとする。Python標準の `json` で読み書きできる構成とする。

| キー             | JSON型                | 内容・形式                                                                     |
| ---------------- | --------------------- | ------------------------------------------------------------------------------ |
| `schema_version` | number（整数）        | ファイル仕様の版。初版は `1`。                                                 |
| `source_url`     | string                | 一覧取得の起点URL。現行の指定値は要件定義書2節を参照する。                     |
| `article_type`   | string                | 選択した記事種別。`"QA"` とする。                                              |
| `collected_at`   | string                | 今回の収集範囲の取得完了日時。ローカル日時の秒精度ISO 8601、UTCオフセット付き。 |
| `urls`           | array（objectの配列） | 累積の記事URLと取得区分。同一URLを重複排除し、本節の格納順に従う。 |

以下にURLオブジェクトと判定規則を定める。

`urls` 配列の各要素は、`url` に記事の絶対URL、`is_new` に新規かどうかを表すJSONの真偽値を格納するオブジェクトとする。

```json
{"url": "https://blackline.my.site.com/BlackLineCommunity/s/article/sample-qa", "is_new": true}
```

初回は比較対象がないため、全URLの `is_new` を `true` とする。2回目以降は前回JSONの `urls` に同じ `url` がなければ `true`、あれば `false` とする。前回の `is_new` の値は判定に使わない。正常実行ごとに前回JSONの全URLを引き継ぐため、過去に保存したURLは保持される。今回現れない保持URLも `false` とし、一覧へ再出現しても取得済みのままとする。

ここでいう取得済みは本アプリでURLを取得したことを指し、別アプリが本文を取得済みであることは意味しない。同一URLの記事本文の更新を判定する要件は含まない。比較対象の選定は3.1節、URLの同一性と成果物の正常完了・履歴の検証方法は4節を参照する。

2026-11-01の追加合意により、1回最大1,000件を収集し、前回JSONの全URLと重複排除して統合した累積一覧を保存する。今回の一覧から外れたURLも削除しない。累積JSONは1,000件を超えてよい。今回の収集に失敗した場合、前回URLだけで完成JSONを作らない。

格納順は、今回のURLを一覧の初出順に置き、今回現れない前回URLを前回の相対順で末尾に追加する。前回A・B、今回B・Cなら、B（false）・C（true）・A（false）となる。保存前に前回全URLが含まれることを検証する。

### 3.1 前回実行の選定（採用済み）

同じ保存先の実行ディレクトリを開始日時順で比較し、開始日時が最新のものを前回実行とする。今回の実行用に作成するディレクトリは比較対象から除外する。JSONの取得完了日時は選定に使用しない。

選定した実行ディレクトリの継続条件と異常時動作は、要件定義書FR-15・4.2節に従う。履歴がまったくない場合だけ初回とする。同時実行に関する制約は要件定義書FR-12に従う。

開始日時順を採用する理由は、実行ディレクトリの日時からユーザーが比較対象を判断でき、手作業で整理する運用と一致するためである。ディレクトリの検証は4.1節を参照する。

## 4. 保存・履歴検証

完成JSONと内部管理状態により、成果物の正常完了と比較元の健全性を検証する。プロセスの終了コードは7節に従う。

### 4.1 日時・URL・JSONの検証

- 実行ディレクトリ名は2.1節の形式に一致し、実在する日時として解析できることを確認する。
- 保存先直下は実行履歴専用とし、実行ディレクトリ以外の項目や解析不能な名前があれば、履歴なしと見なさず停止して手動整理を案内する。
- `collected_at` は3節の形式（例：`2026-11-01T10:30:00+09:00`）で検証する。ディレクトリの開始日時と混同しない。
- URLは一覧のリンクをページURL基準で絶対URLに解決し、文字列完全一致で重複排除・前回比較する。正規化やクエリー削除は行わない。期待形式はHTTPS、ホスト `blackline.my.site.com`、パス `/BlackLineCommunity/s/article/` 配下、認証情報・クエリー・フラグメントなし。異なる形式を黙って変換・除外せず停止する。
- 保存・比較の双方で3節の必須キー・型・版・固定値・有効日時を検証する。整数と真偽値を区別し、非標準数値・重複JSONキー・未知キーは拒否する。
- urls要素は文字列urlと真偽値is_newを必須とし、配列内のURL重複を拒否する。累積件数に1,000件上限を適用しない。
- 正常0件と取得失敗は8.3節の条件で区別する。実機再現を設計確定の条件とせず、ダミー画面・モック応答で検証する。

### 4.2 実行状態と完成JSONの公開

別アプリには利用者が完成JSONのパスを指定して渡す。別アプリに内部状態やハッシュの確認・最新履歴の探索を要求しない。

実行ディレクトリ内の `run-state.json` にrunning・failed・preparedと開始日時を記録する。preparedはJSON検証・公開準備の完了を示し、完成JSONの存在と組み合わせて成果物の正常完了を判断する。完成JSONのSHA-256も内部記録し、次回照合する。別アプリへのJSON項目は増やさない。

1. 設定を検証して開始日時を確定し、今回の実行ディレクトリを排他的に新規作成する。既存名の場合は既存内容へ一切書き込まず停止する。
2. `running` を記録する。今回以外の履歴から3.1節に従って前回を選び、継続条件を検証する。
3. 今回の収集範囲の取得・完全性確認・前回比較・累積統合に成功した後、完成JSONを同じディレクトリの一時ファイルへ書き出す。
4. 書き出したJSONを再読込・検証し、そのハッシュを含む `prepared` を一時ファイルから置換して記録する。成功ログなど公開前に必要な書込みを済ませる。その後、一時JSONを同一ディレクトリ内で完成名 `knowledge-qa-urls.json` へ、既存ファイルを置換しない名前変更で公開する。この公開を成功判定の最終操作とし、公開後の必須ファイル更新は設けない。
5. 公開前の例外時は可能なら `failed` を記録し、ディレクトリと診断情報を残す。強制終了で `running` や一時ファイルだけが残った場合も、正常終了とは扱わない。公開後のログ表示や切断の失敗で、公開済み成果物を未完了へ戻さない。

前回の継続条件は、prepared、開始日時一致、完成JSONの存在と4.1節の検証成功、ハッシュ一致、一時ファイルや公開前失敗の痕跡なしとする。状態ファイルの欠落・破損も異常とし、選定した前回が不適格でも古い履歴へ切り替えない。公開後の後始末失敗は成果物を未完了へ戻さず、これだけを理由に次回比較を拒否しない。内部状態形式と例外処理は詳細設計6〜7節を参照する。

`prepared` の記録後・完成名への公開前に中断した場合は、完成JSONがないため失敗と判定する。公開後にプロセスが中断しても、全検証に成功した完成JSONがあるため、成果物の作成は正常完了と扱う。プロセスの終了コードと成果物の完成を区別する。

未完了ディレクトリには完成名のJSONを作らない。公開時の名前変更の原子性は対応するWindowsの保存先で確認し、ネットワーク共有・同期フォルダー等へ未検証の保証を広げない。手動改変の検出は本アプリの次回比較時に行い、別アプリ側の検証を代行しない。

## 6. 検証方針

ダミーのURL一覧と保存先で、上限付き収集・累積出力・前回比較・過去出力保持・ディレクトリ名衝突を確認する。実施状況は11節、具体的なテスト項目は詳細設計13節を参照する。

前回比較では、初回全件が `true`、前回にあるURLが `false`、前回にないURLが `true` となることを確認する。前回の区分に依存しないこと、今回一覧から外れたURLの保持、保持URLの再出現時も `false` となること、累積1,000件超も確認対象とする。

完全性確認は8節の収集範囲と検出限界に従う。上限1,000件と累積件数を区別し、重複があっても上限外から補充しないことを確認する。

前回の公開前失敗・中断、JSONの破損・欠落、成果物の正常完了を確認できない場合に異常終了すること、古い正常JSONへ自動切替しないこと、ログが停止理由・対象ディレクトリ・手動整理の必要性を示すことを確認する。公開後の後始末失敗だけなら正常な成果物を次回比較に使えることも確認する。履歴がない場合だけ初回とし、整理後の再実行は最初のページから取得する。

前回実行の選定では、開始日時が最新のディレクトリが選ばれること、開始順と完了順が異なる場合も開始日時順で選ぶこと、今回の実行ディレクトリが除外されることを確認する。

### 6.1 検証対象と配布確認

| 対象       | 確認内容                                                                                                                 |
| ---------- | ------------------------------------------------------------------------------------------------------------------------ |
| 保存・履歴 | JSONの必須項目・不正な型・日時・重複、状態やハッシュの不整合、名前解析不能な履歴、保存権限不足、各書込み段階の中断       |
| 一覧取得   | ダミー画面で1ページ・複数ページ、遷移失敗、ページ抜け・逆戻り、件数や順序変化、フィルター解除失敗、ログイン切れ          |
| モーダル   | 対象アンケートの有無・閉鎖失敗、別種モーダルを誤って操作しないこと                                                       |
| 実サイト   | 接続・認証の利用、QAのみの選択、他条件解除、記事リンクと最終ページ判定、観測可能な変化検出。実施結果と検出限界を記録する |
| 配布       | Python未導入のWindows 11でexe・外部設定を使用し、保存・ログ・終了コードを確認。日本語や空白を含むパスも確認する          |

通常テストはダミー情報で行う。実サイトの検証で回答送信などの更新操作は行わない。exeはビルドごとに重複しない `dist/<ビルド日時>/` へ出力し、既存exeを残す。実サイト調査は観察記録、実装・exe実行の結果は実装検証記録を参照する。別端末でのexe配布確認は未実施。

## 7. 構成・処理全体

Windows 11のPython製コンソールバッチとする。製造基準はPython 3.15.2、Playwright 1.64.1、PyInstaller 6.22.3。PyInstallerのonedir形式でexeと同梱依存フォルダー、設定例、起動・復旧説明をまとめて配布する。既存ChromeへCDP接続するためPlaywright用ブラウザーを新規起動・配布しない。これらは製造・検証の開始版であり、exe配布確認済みを意味しない。

責務は、起動と設定読込、Chrome接続と一覧操作、URL収集と完全性確認、前回比較と保存、診断ログに分ける。具体的なファイル・クラス構成は詳細設計で定める。

処理順は「設定検証 → 開始日時・期限確定 → 実行領域作成 → 履歴検証 → Chrome接続 → 一覧・絞り込み初期化 → 今回収集・完全性確認 → 累積統合 → 一時JSON検証・prepared記録 → 完成JSON公開 → タブ閉鎖・切断 → 終了」とする。収集中の進捗を保存して再開する処理は設けない。

すべて成功した場合は終了0、失敗時は終了1。公開後にタブ閉鎖・切断だけが失敗した場合も終了1とするが、完成JSONとpreparedは正常完了のまま保持する。成果物の正常完了とプロセス終了コードを区別する。

## 8. Chrome接続・一覧取得

### 8.1 接続と利用者の準備

ユーザーは専用Chromeプロファイルをデバッグ接続可能な状態で手動起動し、ログインする。通常利用プロファイルのCookieやログイン情報をコピーしない。接続先は9節の設定で変更でき、初期値は `http://127.0.0.1:9223` とする。

Playwright同期APIのconnect_over_cdpで接続し、認証済みの既定コンテキストに処理用タブを1つ作る。認証を利用できなければ停止する。終了時は所有タブだけを閉じ、ランタイムを停止して切断する。browser/context全体のcloseを呼ばず、利用者の既存タブとChromeを維持する。

#### 起動・接続の準備手順

以下は利用者向けの準備手順である。実サイトの観察結果は観察記録と区別する。

1. Chromeのインストール先をショートカットのプロパティ等で確認する。例は `C:\Program Files\Google\Chrome\Application\chrome.exe`。端末により異なるため、存在しない場合は実際のパスを使う。
2. 専用データフォルダーは `%LOCALAPPDATA%\BlackLineKnowledge\ChromeUserData` とする。保存JSONの親フォルダーとは別に置き、初回はこのプロファイルでログインする。
3. 下記PowerShell例で専用Chromeを起動する。同じ専用データフォルダーのChromeが既に起動している場合は、その専用ウィンドウを閉じてから再起動する。通常利用のChromeを一括終了する操作は行わない。

```powershell
$knowledgeChromeExe = 'C:\Program Files (x86)\Google\Chrome\Application\chrome.exe'
$knowledgeChromeData = Join-Path $env:LOCALAPPDATA 'BlackLineKnowledge\ChromeUserData'
if (-not (Test-Path -LiteralPath $knowledgeChromeExe -PathType Leaf)) {
    throw 'Chromeの実際のインストール先を指定してください。'
}
# 専用の対話用Chromeを表示し、利用者がログインする。
Start-Process -FilePath $knowledgeChromeExe -ArgumentList @(
    '--remote-debugging-port=9223'
    ('--user-data-dir="{0}"' -f $knowledgeChromeData)
    'https://blackline.my.site.com/BlackLineCommunity/s/knowledge'
)
```

4. 起動した専用Chromeで利用者がBlackLineへログインし、Knowledge一覧が表示できることを確認する。ログイン情報を設定ファイルへ書かない。
5. 同じPCのPowerShellから下記の確認を行う。取得した接続情報の全文は出力せず、Chrome系の識別と接続情報の有無だけを表示する。

```powershell
$knowledgeCdp = Invoke-RestMethod -Uri 'http://127.0.0.1:9223/json/version' -TimeoutSec 5
[pscustomobject]@{
    Browser = $knowledgeCdp.Browser
    HasDebuggerEndpoint = [bool]$knowledgeCdp.webSocketDebuggerUrl
}
```

6. 成功時も、これはデバッグ接続口の応答確認までとする。Knowledgeへのログイン利用・新規タブ作成・DOM取得の成功は、その後の接続検証で確認する。アプリ実行中は専用Chromeを開いたままにする。

応答しない場合は、専用Chromeの有無、専用データフォルダーと起動引数、ポート9223の競合、端末ポリシーを順に確認する。別アプリのプロセスを勝手に停止しない。ポートを変える場合はChromeの起動値とchrome_endpointを一致させる。外部公開のためのファイアウォール変更や全アドレス待受は行わない。

根拠は [Chrome公式のデバッグ起動変更](https://developer.chrome.com/blog/remote-debugging-port) と [Playwrightの既存ブラウザー接続](https://playwright.dev/python/docs/api/class-browsertype#browser-type-connect-over-cdp) を参照する。`/json/version` の疎通と本作業セッションのブラウザー操作ホストは別の接続経路であり、一方の成功で他方の利用可能性を判断しない。

### 8.2 絞り込み・ページ遷移

必要時にClear Allで全解除し、QAだけを選択する。CATEGORYの同名QAは選択しない。再読込だけで初期化済みとせず、画面と要求条件で反映を確認する。チェック状態はShadow DOMを探索するPlaywrightロケーターで取得する。0件以外は1ページ目で収集を始め、言語で除外しない。

各ページの番号・総数・記事リンク順序を観測し、Nextを1回操作して対応する応答とDOMの更新を待つ。最終ページは現在番号と総数の一致、Nextのbutton--disabledクラスを併用して判定する。disabled属性だけで判断しない。総ページ数50は固定せず、1,000件到達も正常終端とする。上限は重複排除前の件数で数え、重複分を範囲外から補充しない。

URLは一覧のタイトルリンクから取得する。通常の画面操作から発生した一覧・件数アクションを要求IDと対応付けて監視し、期待フィルター・ページのHTTP/action成功、総ページ数、記事種別、応答urlName列とDOMリンク列の順序付き一致、読み込み終了を確認する。照合時だけDOMパス末尾をデコードし、保存URLは変更しない。DOMの一時消失は期限内で再観測する。古い応答や最初のXHR完了だけで先へ進まず、内部APIへ独立した要求は送らない。具体的な監視とセレクターは詳細設計8〜9節を参照する。

提示されたアンケートが表示されたら、そのアンケート内の下部Closeを押し、閉じたことと中断した操作の状態を確認して続行する。他のモーダルや閉鎖失敗で処理できない場合は停止する。識別セレクターの具体化は詳細設計・実装で行い、不定期の実機出現を基本設計確定の条件としない。

### 8.3 完全性の確認と限界

ページ番号の飛び・逆戻り・意図しない再遷移、総ページ数や観測できる総件数の変化、応答とDOMの不一致を検出したら停止する。記事URLの重複や同一リンク列だけでは未遷移と断定せず、対応応答とページ状態で判断する。

ユーザー合意により1回走査だけを行い、再走査は行わない。件数不変の入れ替わり・未訪問ページ間の移動・上限外の変化は保証対象外とする。記事別更新日時を一覧全体の変更識別子とせず、同一時点の一覧であることも保証しない。

QAのみ・CATEGORYなし、件数APIの正常0、記事取得SUCCESSの空配列、DOMリンク0件、読み込み終了が一致した場合は正常0件とする。前回URLは全件保持しis_new=false、初回は空のurls配列を保存する。0件時はページ番号・Next・特定の空表示文言を必須としない。通信失敗や不一致は正常0件ではなく異常終了とする。

## 9. 設定・待機時間

`settings.toml` はexeと同じディレクトリから読み、相対パスは設定ファイル基準で解決する。以下の全項目を必須とし、省略・不正値は停止する。初期値は設定例に記載する値であり、欠落時に自動適用する既定値ではない。時間は有限数値、操作・全体は正、ページ間隔は0以上とする。

| パラメータ                | 用途                                                   | 設定例の初期値                |
| --------------------------- | ------------------------------------------------------ | ----------------------- |
| `output_dir`                | 実行ディレクトリを作る親フォルダー。ファイル名ではない | 利用者が指定            |
| `chrome_endpoint`           | 既存Chromeへの接続先。ループバックのHTTPのみ許可し、認証情報・クエリー・フラグメントを拒否 | `http://127.0.0.1:9223` |
| `page_interval_seconds`     | 次ページ操作の前に置く最小待機時間（秒）               | 2                       |
| `operation_timeout_seconds` | 接続・画面更新など1操作の待機上限（秒）                | 30                      |
| `run_timeout_seconds`       | 起動から保存完了までの全体上限（秒）                   | 3600                    |

固定待機だけで完了を判断しない。各操作には操作期限と全体の残り期限の小さい方を適用し、時間切れ・遷移失敗で停止する。自動の全体再試行は行わず、アンケートで期限をリセットしない。50ページ時のページ間待機だけなら約98秒だが、所要時間の保証ではない。

起点URL・記事種別・完成JSON名は固定とする。設定例は用途・単位・パスの意味をコメント付きで実装時に作成する。

## 10. エラー・ログ

実行ディレクトリのapp.logに開始・段階・ページ番号・件数・公開準備・停止理由を記録する。ディレクトリ作成前の失敗は既存履歴へ書かず、exe配下の専用logsへ一意な起動エラーログを作る。書込み不能時は標準エラーへ出して終了1とする。公開後のログ更新は成功判定の必須条件にしない。

ログにはCookie・トークン・パスワード・ページHTML・アカウント表示を含めない。ブラウザー例外の全文やURLのクエリーを無加工で出さず、診断に必要な分類と安全なメッセージを記録する。

| 異常                             | 動作・利用者への案内                                                  |
| -------------------------------- | --------------------------------------------------------------------- |
| 設定不正・接続失敗               | 対象設定またはChrome起動状態の確認を案内して停止                      |
| ログイン切れ                     | Chromeでの再ログイン後の再実行を案内して停止                          |
| 履歴不正・前回未完了             | 停止理由・対象ディレクトリと、要件4.2節の手動整理の案内を記録して停止 |
| 取得失敗・途中変化・上限時間超過 | 完成扱いにせず、履歴整理後の最初からの再実行を案内                    |
| 保存失敗                         | 完了状態を記録せず、保存先・権限・空き容量の確認を案内                |

対象一覧の要求失敗・HTTPエラー・action失敗・通信待機タイムアウトは異常終了1とし、公開前なら今回の完成JSONを作らない。無関係な広告・計測通信は対象に含めない。公開後の閉鎖・切断失敗は7節に従う。

## 11. 検証状況と後続確認

実サイト調査ではCDP接続、QA選択、Clear AllとQA再選択3回、表示上の50ページ・各20件・重複なし1,000URL、固定待機なしの49/50ページ間4遷移を確認した。Shadow DOMとURLエンコード差への対応も観察記録に記載している。調査時の失敗と訂正を含む経緯は観察記録に保持する。

実際の0件表示は再現できず、アンケートの自然出現も確認できていない。ユーザー合意により、これらを設計確定のための実機待ち条件とはしない。正常0件・アンケートClose・通信失敗時の終了/公開抑止は詳細設計とダミー・モック検証で扱う。具体的なアンケート識別セレクターは未取得であり、未知のCloseボタンを推測で操作しない。

アプリ実装・自動テスト・実Chrome収集・exeビルドの実施結果は[実装検証記録](implementation-validation.md)を参照する。Python未導入の別Windowsでの配布確認・保存先の電源断時の耐久性や同期競合下の原子性確認は未実施。設計上の採用と検証成功を区別する。

### 技術選定の根拠

- [Chromeのデバッグ起動変更](https://developer.chrome.com/blog/remote-debugging-port)：専用user-data-dirを使用する前提。
- [Playwright CDP接続](https://playwright.dev/python/docs/api/class-browsertype#browser-type-connect-over-cdp)：既存Chromium系ブラウザーと既定コンテキストの利用。Playwright独自プロトコルより機能制約があることに留意する。
- [PyInstaller配布形式](https://pyinstaller.org/en/stable/operating-mode.html)：onedirでPythonと依存物を同梱し、対象OS・Pythonに対応する環境でビルド・確認する。
