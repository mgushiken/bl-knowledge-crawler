# 1ページ取得アプリ 詳細設計

## 1. 位置付けと状態

[要件定義書・基本設計書](design.md)を正本とし、14～16節の初期段階を実装可能な単位に具体化する。基本設計と矛盾する場合は本書で上書きせず、相違点を確認する。

複数ページ版の基本設計案は[基本設計書19節](design.md#19-複数ページ取得の基本設計案)に記載する。本書は完成済みの1ページ取得版の設計・検証記録として維持し、巡回・進捗・一巡履歴の詳細設計は基本設計の確定後に別途作成する。

共通処理と、提供された2ページの保存HTML・描画後DOM・スクリーンショットから確認できた抽出条件を定義する。本実装前の技術検証結果は16節、本実装の状態と検証結果は17節を参照する。過去時点の「未実施」「候補」は当時の記録として残す。巡回・自動リトライ・通知処理は初版に含めない。

2026-10-26の文書整理時点でも、本書の適用範囲は1ページ取得版である。16節の検証用innerText保存と17節の本番Markdown出力を区別し、後続の確認結果で過去の実験記録を上書きしない。複数ページ版の現在の根拠と未確認事項は基本設計19.10・19.11節に集約する。

## 2. モジュールとデータ

配置先は `src/bl_documents_crawler/`。下表の各モジュールと、URL・日時・ハッシュ・固定コード例外を扱う`common.py`を実装した。起動入口はルートの`run_crawler.py`。検証コードを本番から参照しない。

| モジュール | 主な関数・責務 |
| --- | --- |
| `__main__.py` | `main() -> int`：起動・終了、共通例外処理 |
| `config.py` | `load_settings(base_dir) -> Settings`：設定読込と検証 |
| `browser.py` | `fetch_page(settings, workspace)`：接続・記事と画像の取得・タブ解放 |
| `document.py` | `build_document(snapshot, images) -> DocumentCandidate`：変換・メタデータ・内容ハッシュ |
| `storage.py` | `scan_existing(root)`、`plan_save(...)`、`commit_save(...)`：照合・配置・反映 |
| `operations.py` | `write_error(...)`、`write_completion(...)`：運用ファイルの出力 |

データは単純なdataclassで扱い、責務を持たない基底クラスや汎用プラグインは設けない。

| データ | 主な項目 |
| --- | --- |
| `Settings` | 起点URL、CDP接続先、3種のタイムアウト、3種の出力先 |
| `PageSnapshot` | 元URL、表示後URL、タイトル、記事自身を含む階層、記事HTML、取得日時 |
| 取得結果 | PageSnapshotとImageAsset一覧の組。タブ解放後にも使用できるデータのみを返す |
| `ImageAsset` | 記事内識別子、全64桁ハッシュ、拡張子、一時ファイルのパス |
| `DocumentCandidate` | タイトル、元URL、階層、本文、内容ハッシュ、画像一覧、取得日時 |
| `ExistingDocument` | Markdownのパス、検証済みフロントマター |
| `SavePlan` | new / unchanged / update / relocate、旧パス、新パス、引継ぎ日時 |

バイト列を含む画像・HTML・ブラウザオブジェクトをログへ渡さない。取得処理は自分が作ったタブをfinallyで閉じ、接続を解放する。既存Chromeを維持できる終了方法は接続検証で確定する。

## 3. 設定検証

- exe実行時は `sys.executable` の親、ソース実行時はプロジェクトルートを基準に `settings.toml` を読み込む。作業ディレクトリやPyInstaller展開先を基準にしない。
- `source.start_url` と `storage.output_dir`、`storage.error_dir`、`storage.completion_file` は必須の空でない文字列。
- `browser.cdp_url` の既定値は `http://127.0.0.1:9222`。HTTP(S)形式でループバックのホストのみ許可する。接続先のユーザー情報・クエリ・フラグメントは許可しない。
- タイムアウトは基本設計の既定値30 / 60 / 60秒。真偽値を数値として受け付けず、有限の正数とする。APIへ渡す時点でミリ秒へ変換する。
- 起点URLはHTTP(S)、ホスト必須、ユーザー情報なしとする。クエリを変更せず保持するが、ログではクエリとフラグメントを除去する。元URLの保存とログのマスキングを混同しない。
- 保存先は設定ファイル基準で絶対パスに解決する。ドライブ指定のない相対パスを受け付け、`C:folder` のようなドライブ相対パスは拒否する。
- `output_dir` と `error_dir` は一致・包含関係にしない。完了日時ファイルは両フォルダの外に置き、Markdownやエラーファイルと同じパスにしない。
- 不明なセクション・キーは設定ミスとして異常終了する。外部設定を勝手に書き換えない。
- 必須値検証後に出力先を作成する。フォルダであるべき場所にファイルがある場合等は `CONFIG_ERROR` とする。書込権限は実際の作成・保存時にも検証する。
- 設定の構文・型検証が済むまでは設定内のエラーフォルダを信頼せず、失敗時はexe所在への代替出力と標準エラーを使う。

## 4. URL・日時・ハッシュ

- 元URLは基本設計15.1節の正規化結果。`source_url` とURLハッシュの入力を一致させる。リダイレクト後URLを採用する条件は11節の確認事項。
- 日時は `datetime.now().astimezone().isoformat(timespec="seconds")` 相当の文字列に統一する。OSのタイムゾーンを用い、UTCオフセットを必須にする。
- 取得日時は必要な記事情報と画像の取得が正常に完了した時点、作成・更新日時は最終反映直前、完了日時は反映と後片付けが成功した後に採取する。
- 画像ハッシュはファイルバイト列のSHA-256。URLハッシュは正規化元URLのUTF-8バイト列のSHA-256。比較には小文字16進表記の全64桁を使う。
- 内容ハッシュは `title + "\n" + normalized_body` のSHA-256。本文のCRLF・CRはLFに変換し、末尾のLFだけを除いてLFを1つ追加する。本文の途中の空白は保持する。
- ハッシュ用本文では、画像要素の参照先を `bl-image-sha256:<全64桁>` にする。表示用本文と同じ変換工程で生成し、最終Markdownを文字列置換で再解析しない。altや画像の位置は本文に残す。
- 内容ハッシュにフロントマター、保存ルート、取得日時を含めない。変換器の設定・バージョンを固定し、再実行で出力が安定することをダミーHTMLで確認する。
- 比較用画像一覧は保存ルート相対パスと全ハッシュの組を重複排除・パス順でソートする。本文の画像順序は変更しない。

## 5. フロントマターと既存記事の検証

- 基本設計15.1節のキーを同じ順序で出力し、安全なYAMLローダー・ダンパーを使用する。具体的なパッケージは変換検証と合わせて選定する。
- `title` / `source_url` は文字列、`menu_path` は空でない文字列の配列、`content_hash` は `sha256:` と64桁の小文字16進数。`menu_path` の末尾は記事タイトルと一致させる。
- `created_at` / `fetched_at` はタイムゾーン付き日時文字列、`updated_at` はnullまたは同形式の文字列。YAMLによる暗黙の日時型変換には依存しない。
- `images` は配列で、各要素に保存ルート相対パスとハッシュを必須とする。絶対パス・ルート外参照を拒否する。
- 管理対象は専用の `output_dir` 配下のMarkdown。`assets` とアプリの一時ファイルは走査対象外。無関係なMarkdownを混在させない運用とする。
- フロントマター欠落・キー重複・型不正・元URL重複・読込失敗は `EXISTING_DATA_ERROR` とし、上書き前に停止する。ファイル名の短縮ハッシュだけで記事の同一性を判断しない。
- 既存ハッシュは前回取得内容の比較用として扱う。保存済みファイルへの人の追記を取り込む機能は設けず、出力資料は生成物として運用する。

## 6. 名前とパス

- パス要素はタイトル・メニュー項目ごとに処理する。`< > : " / \ | ? *` と制御文字U+0000～U+001Fを `_` に置換し、末尾の空白・ピリオドを除く。結果が空なら `_` とする。
- Windows予約名（拡張子付きも含むCON / PRN / AUX / NUL / COM1～9 / LPT1～9、および対象となる上付き数字）には先頭 `_` を付ける。元の文字列はフロントマターで保持する。
- 同じ親の別メニュー名が置換後に同じになる場合や、大文字小文字のみで衝突する場合は、推測で階層を統合せず `PATH_COLLISION` で終了する。階層名の自動サフィックス追加は初版では行わない。
- 長い要素・長い絶対パスは黙って切り詰めない。初版ではパス要素255 UTF-16コード単位以下、ローカル絶対パス259単位以下を事前確認し、超過時は `PATH_TOO_LONG` で終了して保存先の短縮を案内する。これは初版の保守的なローカル上限であり、SharePoint同期可否の保証ではない。
- Markdownのファイル名だけは基本設計のURLハッシュ延長規則を使う。前回すでに延長済みでタイトル・階層が同じならそのパスを再利用し、不要な改名を避ける。
- 作成・削除・置換前に解決済みパスが想定ルート内にあることを確認する。ジャンクション・シンボリックリンク経由でルート外へ書き込まない。
- Markdown中の相対画像パスは `/` 区切りとし、リンク先の空白・括弧などをエスケープする。URLハッシュと画像ハッシュで画像名を構成するため、画像名自体はASCIIに限定される。

根拠： [Windowsの命名規則](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)、[OneDriveとSharePointの制限](https://support.microsoft.com/en-us/onedrive/restrictions-and-limitations-in-onedrive-and-sharepoint)（2026-10-25確認）。同期サービス側のサイト相対パス長などはローカルパスだけでは判定できない。

## 7. 保存と処理状態

通常の順序は `config → scan → fetch → convert → compare → save → cleanup → completion`。各段階名をエラーの `stage` に使う。

| 判定 | 条件と保存 |
| --- | --- |
| new | 元URLの既存記事なし。created_atを設定、updated_atはnull |
| unchanged | 内容・画像・タイトル・階層が一致。既存Markdownを更新しない |
| update | 同じ配置で内容等に変更。created_atを保持、updated_atを設定 |
| relocate | 同じURLでタイトル・階層が変更。新配置に保存後、旧Markdownを削除 |

- 一時領域は `%LOCALAPPDATA%/BlackLineCrawler/tmp/<UUID>/`。今回作成したフォルダだけを対象にし、他実行の残留物を自動削除しない。同期対象外であることは配置運用で確認する。
- 全画像の取得成功と文書生成後に最終反映する。画像を最終フォルダ内の一時ファイルへ書き、閉じてから確定名へ置換する。既存の同名画像はバイト列ハッシュが一致することを確認する。
- Markdownは新しいフロントマターと本文全体を生成して一時ファイルへ出力し、同じフォルダ内で置換する。最終配置にあるファイルの元URLは置換直前にも確認する。
- 書込はバイナリで行う。画像は取得したバイト列を変換せず保持し、Markdown・完了日時はUTF-8 BOMなし・LFに固定する。書込後にflush、fsync、closeしてから置換する。OS・同期サービス・電源断を含む完全な耐障害性は保証しない。
- 画像とMarkdownの反映順序は基本設計に従う。無変更時も、一時領域・タブの後片付けを済ませて完了日時を更新する。
- 完了日時のファイル内容は日時文字列とLFのみ。親フォルダ内の一時ファイルで置換し、失敗時は終了コード1。直前のMarkdown保存が成功していても取り消さない。
- 日付・実行識別子入りのログや一時ファイルは既存ファイルを上書きしない方法で作成する。

## 8. 異常終了後の再実行

基本設計どおり自動再起動・一括ロールバックをしない。

| 失敗箇所・残留物 | 再実行時の扱い |
| --- | --- |
| 最終反映前 | 既存Markdownを保持。残った実行別一時領域は人が確認して削除できる |
| 画像のみ反映済み | 画像ハッシュ一致を確認して再利用。参照されない画像も自動削除しない |
| Markdown反映後、完了日時更新前 | 同じ内容なら無変更として処理し、正常終了時に完了日時を更新 |
| 改名後の旧Markdown削除失敗 | 同一URLの重複を検出して停止。人が画像参照・内容・created_atを確認して旧版を除去してから再実行 |
| 最終フォルダの一時ファイル | 既存記事の走査対象から除外。人が実行停止を確認してから削除 |

未完成ファイルから新旧を推測して自動復旧しない。ログに処理段階と対象を記録し、人が対応できるようにする。

## 9. エラー出力

- ファイル名は `error-<UTC年月日時分秒マイクロ秒>-<UUID>.json`。内容の `occurred_at` はタイムゾーン付きISO 8601文字列。`source_url` はクエリ等を除去したログ用URL、未取得時はnull。
- `error_code` は `CONFIG_ERROR`、`BROWSER_CONNECT_ERROR`、`AUTH_ERROR`、`PAGE_FETCH_ERROR`、`EXTRACTION_ERROR`、`IMAGE_FETCH_ERROR`、`CONVERSION_ERROR`、`EXISTING_DATA_ERROR`、`PATH_COLLISION`、`PATH_TOO_LONG`、`SAVE_ERROR`、`CLEANUP_ERROR`、`COMPLETION_WRITE_ERROR`、`UNEXPECTED_ERROR` を基本とする。
- HTTP 401 / 403は `AUTH_ERROR`、通信・タイムアウトは取得対象に応じたFETCHエラー。初版はいずれもリトライせず終了コード1。
- `message` は人が原因と次の対応を理解できる固定文を基本とし、例外全文・レスポンス本文・認証値・画像URLを直接埋め込まない。
- 取得エラー後のタブ解放等も失敗した場合、元のエラーを保持し、後片付けエラーを別ファイルにする。ログ出力失敗そのものを再帰的にログ出力しない。
- 指定先→exe所在の順でファイル出力を試し、代替出力時は標準エラーにも表示する。両方失敗しても終了コード1を保持し、標準エラーへの表示を試みる。

## 10. 検証への対応

基本設計16.1節に加え、詳細設計で決めた次の境界をダミーデータで検証する。

- 設定内のbool・NaN・未知キー・ドライブ相対パス、出力先の包含。
- 改行のみの違い、画像alt・順序・差し替え、日時変更だけでのハッシュ不変。
- 禁止文字・予約名・大文字小文字・置換後の階層衝突・UTF-16長・ルート外パス。
- フロントマター欠落・重複キー・日時型・重複URL、延長済みファイル名の再利用。
- 各反映境界での書込失敗と再実行、旧Markdown削除失敗時の停止、完了日時の非更新。
- 例外文にダミートークンを含ませてもログ・標準エラーへ露出しないこと。

### 12.2 設定ガイドの抽出条件候補

- タイトル候補：`#main-content h1.article-title` のテキスト。ヘッダー固定表示のタイトルを重ねて取得しない。
- 本文候補：`#main-content d360-article#articleContent article.editor360-preview-content`。1個の要素に特定でき、空でないことを確認する。属性名の `_ngcontent-*` や自動生成された見出しIDには依存しない。
- 本文には「概要」から「主要用語」までの見出しと5個の表が含まれる。開始・終了のスクリーンショットに表示された本文・最終表との対応を確認した。途中の全画面との照合は未実施。

## 13. 取得処理の詳細

### 13.1 ブラウザ操作の順序

1. `sync_playwright()` で接続用ランタイムを開始し、設定の接続タイムアウトで `chromium.connect_over_cdp()` を呼ぶ。
2. 既定コンテキストを取得し、存在しなければ `BROWSER_CONNECT_ERROR`。新規の分離コンテキストは作らず、ログイン済みコンテキスト内に作業タブを1個作る。
3. `page.goto(start_url, wait_until="domcontentloaded")` を実行する。移動開始時に単調時計からページ期限を計算し、以降の描画待ちにも残り時間を渡す。移動と抽出の各段階で60秒ずつ待つ構造にはしない。
4. 主文書の最終HTTP応答が401・403なら `AUTH_ERROR`、それ以外の400以上は `PAGE_FETCH_ERROR`。主フレームのnavigation requestに対応するresponseイベントをgoto前から監視し、goto返り値と合わせて判定する。実証では空の401でgoto自体が例外になったため、例外時も観測済みステータスを確認する。応答を取得できなければ成功扱いにしない。
5. 12節のタイトル、カテゴリ型または記事型本文、現在メニュー項目、連続した階層を、残り時間内で待つ。本文型は1種類・1要素に特定する。非表示要素や読み込みプレースホルダーだけの状態を受け付けない。
6. タイトル・本文HTML・階層・画像参照を、同じDOM評価処理で文字列・配列として採取する。取得途中でURLや現在項目が変わった場合は `EXTRACTION_ERROR`。生きたElementHandleを変換・保存層へ渡さない。
7. 画像を逐次取得し一時領域に保持する。全取得成功後に取得日時を採取し、`FetchResult` を構成する。
8. 自分のタブを閉じてPlaywrightランタイムを停止し、Chromeとの通信を解放してから呼出元へ戻る。既定コンテキストの `close()`、Chrome全体を終了させる操作は呼ばない。ランタイム停止で外部Chromeが維持されることは実機検証項目とする。

待機中のDOM再評価は描画を待つ操作であり、取得要求の自動リトライとは区別する。再度の `goto`、reload、HTTP要求の再送による復旧は行わない。解析・変換はブラウザ解放後のローカル処理にする。

### 13.2 URLと認証判定

- 記事の識別には設定の起点URLを正規化した値を使い、表示後URLとcanonicalは照合用に採取する。canonicalだけを根拠にファイル識別子を変更しない。
- 表示後URL・canonicalと起点URLが同じ正規化結果なら通常の処理を行う。異なる場合の許可範囲は現状未検証なので、誤ったページを保存せず `EXTRACTION_ERROR` とする。認証リダイレクトの実例確認後、必要な扱いを設計へ反映する。
- 200応答のログイン画面は401とは区別し、未確認のURL文字列や画面文言をコードに固定しない。既知の本文が期限内に表示されなければ `EXTRACTION_ERROR` とし、「再ログインまたは画面構造の確認が必要」と案内する。
- サイトの全通信へグローバルな401/403監視を付けない。主文書と明示的に取得する画像の応答を対象とし、ユーザーの別タブや無関係な解析サービスの通信を混ぜない。

### 13.3 画像取得

- 各本文 `img` の `currentSrc`、`src`、alt、本文中の順序を採取する。`currentSrc` が空なら `src` を使い、相対参照は表示後URLを基準に解決する。画像のURLをファイル名には使わない。
- HTTP(S)画像はログイン済みコンテキストの `context.request.get()` で取得する案とする。Cookieはコンテキストで共有されるが、ブラウザの全認証状態・Referer依存・CDN応答を同一に再現できるとは限らないため実機確認する。
- `max_retries=0`、設定の画像タイムアウト、HTTPエラーを応答から判定できる設定を明示する。レスポンスはバイト列を一時保存した後に解放し、既存コンテキストの共有requestオブジェクト自体をdisposeしない。
- 同一の解決済みURLは1実行内で1回だけ取得し、本文の複数箇所から参照できるようにする。違うURLが同じ画像データを返す場合は画像ハッシュで重複排除する。
- 401・403は `AUTH_ERROR`、他の400以上・空応答・画像以外のContent-Type・取得タイムアウトは `IMAGE_FETCH_ERROR`。拡張子はURL末尾ではなく、Content-Typeと画像バイト列の形式確認で決める。形式が一致しなければ保存しない。
- PNG / JPEG / GIF / WebPをダミー応答で検証する対象とし、実際の対応形式は検証結果をもとに固定する。SVG / data URI / blob / lazy-load専用属性は無条件に捨てず、出現時の対応を確定するまでは明示的な取得エラーにする。
- 画像の自動再送や、失敗時に認証値をコピーして別クライアントで再取得する回避処理は設けない。画像の削除・差し替え後の旧ファイル整理は後続検討のままとする。

根拠： [Playwright APIRequestContext](https://playwright.dev/python/docs/api/class-apirequestcontext)（Cookie共有、max_retries、HTTP応答の取扱い。2026-10-25確認）。このAPIの採用は取得成功の実証ではない。

## 14. HTMLからMarkdownへの変換設計

### 14.1 ライブラリの候補と採用条件

- HTML解析はBeautiful Soup 4と標準の `html.parser`、HTML→Markdownは `markdownify`、YAMLはPyYAMLを候補とする。HTML変換器をゼロから作らず、画像・表など必要な部分だけ調整する。
- 現段階では候補選定までとし、依存ファイルへの追加・パッケージのインストールは行っていない。正確なバージョンはダミーfixture検証・Windows 11の配布検証が可能な組合せで固定する。開発ブランチの最新版に無条件で追従しない。
- Markdown変換器の初期設定案は `heading_style="ATX"`、`bullets="-"`、`wrap=False`、`autolinks=False`、`table_infer_header=False`。設定名と動作は固定するリリースで確認する。
- PyYAMLはSafeLoaderを基礎に重複キー拒否を追加する。SafeLoaderを呼ぶだけでは重複キー検証の代わりにならない。出力は安全なダンパーでUnicodeを保持し、キー順を固定、日時を文字列として出力する。

根拠： [markdownify公式README](https://github.com/matthewwithanm/python-markdownify/blob/develop/README.rst)、[PyYAML公式資料](https://pyyaml.org/wiki/PyYAMLDocumentation)（2026-10-25確認）。候補選定の根拠とし、検証済みバージョンの記録とは区別する。

### 14.2 前処理と出力

1. 抽出済み本文だけを解析する。HTML全体を変換器へ渡さない。script・style・操作用button・表示用アイコンを除く。本文の説明文・リンク・画像・表は残す。
2. 相対リンクを表示後URL基準でHTTP(S)の絶対リンクに解決する。フラグメントのみのリンクも元ページ内の位置を指す絶対リンクとし、クロールはしない。危険な実行スキームをそのまま出力しない。
3. 画像ごとに取得済みImageAssetを対応させる。同じ解析結果から、表示用の相対パスを使う本文と、ハッシュ用の画像識別子を使う本文を生成する。未取得画像のまま文書を確定しない。
4. 見出し階層・太字・斜体・段落・箇条書き・引用・コードを維持して変換する。記事タイトルは別にH1として1回だけ付与し、本文に存在する同名の見出しを無条件で一括削除しない。
5. 4節の改行規則で正規化し、内容ハッシュを計算する。フロントマターは既存記事との照合後に日時を決めて付与する。

カテゴリ型Consolidationでは案内タイトルのリンク、記事数、公開日、概要を出力する。`Next`、コピーリンク操作、フォルダ等の装飾は出力しない。設定ガイドでは抽出された記事本文だけを変換する。

### 14.3 表と画像の変換品質

- 提供された設定ガイドの本文には5個の表があり、確認した全87セルのrowspan・colspanは1。現資料にはセル結合の実例がない。
