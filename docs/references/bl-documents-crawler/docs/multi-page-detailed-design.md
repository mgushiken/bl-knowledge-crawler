[1ページ版詳細設計](detailed-design.md)は完成済み初期版の記録として維持する。本書では継続巡回に必要な差分を定義する。設計作成時は本番コード・実設定・設定サンプル・過去のdist成果物を変更せず、設計PRのマージ後に共通基盤の実装を開始した（22節）。実設定・既存distは引き続き変更しない。通常の検証はダミー限定とし、実BlackLineの巡回は行わない。

## 2. 既存コードとの接続と責務

Python・同期Playwright・逐次処理を維持する。新規ライブラリ、DB、並列取得、汎用プラグインは追加しない。本番からvalidationをimportしない。同一の保存先・進捗を使用するアプリは同時実行しない運用とし、今回ロック機構を独断で追加しない。

| 配置              | インターフェース案・責務                                                                                                                                      |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `__main__.py`     | `main() -> int`で設定読込後に分岐。singleは現行経路、continuousは`run_continuous(settings)`へ。固定コードによる停止ログと終了コードを集約                     |
| `config.py`       | Settingsへcrawl設定を追加。全値・パスの検証後に、そのモードで使う出力先だけ準備                                                                               |
| 新規`crawler.py`  | `run_continuous(settings) -> int`、`process_target(...) -> PageOutcome`、`wait_interval(...)`。状態遷移、保存・出力の確定順、手動終了を管理                   |
| 新規`progress.py` | `load_progress(settings) -> Progress または None`、`validate_progress(...)`、`save_progress(...)`。重複キー検出、全項目検証、置換保存                         |
| 新規`menu.py`     | `discover_targets(settings) -> Target一覧`。列挙専用の接続・タブを解放してから返す。未完成一覧を返さない                                                      |
| `browser.py`      | `fetch_page(settings, workspace, target=None)`。target未指定のsingle呼出しを維持し、continuousは対象URL・固定階層を明示。取得と観測、例外分類、タブ解放を担当 |
| `document.py`     | 既存PageSnapshot・ImageAsset・変換を使用。固定階層を反映済みのスナップショットを受け取る                                                                      |
| `storage.py`      | scan_existing・plan_save・commit_saveを使用。保存結果からメモリ上のURL対応表を更新できるようにする                                                            |
| `operations.py`   | `write_completion(path, completed_at=None)`、`write_skip(...)`、`write_cycle_result(...)`を追加・拡張。singleの日時省略呼出しを維持                           |
| `common.py`       | normalize_url・log_url・日時・固定コード例外を再利用。スキップ判定を文字列メッセージから推測しない                                                            |

### 2.1 現行との差分と影響

- 現行`fetch_page`はsettings.start_urlだけを取得し、SNAPSHOTは可視DOMから全祖先を再構成してタイトルとの一致を要求する。continuousでは固定一覧の親階層と実際の現在位置を分離する。singleの厳格な既存条件は維持する。
- 現行`page_status_error`は末尾ステータス中心で、記事APIを監視しない。continuousでは経路全体の401/403と転送を分類する。サイト固有APIの関連付けは11節の確定後に実装する。
- 現行画像取得は一時ファイルへの書込失敗をIMAGE_FETCH_ERRORへまとめ得る。continuousでこのコードだけを見てスキップするとローカルI/O失敗を隠すため、通信・デコードとファイル操作の例外境界を分ける。
- 現行`commit_save`のSavePlan.kindはnew／update／relocate／unchanged。集計はnew／updated／unchangedへ写像し、updateとrelocateをupdatedへ1件だけ加算する。
- 現行`write_completion`は呼出時刻を採取する。continuousでは保存済み日時を引数で受け取り、再開時にも同じ内容を出せるようにする。
- 現行`write_error`は指定先への保存失敗を呼出側へ返さない。スキップ出力をこの戻り値に依存させない。専用write_skipは指定先保存の成否を明示し、代替出力に成功しても巡回を停止する。
- 現行mainはExceptionを扱い、KeyboardInterruptを通常終了へ接続していない。continuousの最上位で捕捉し、タブ・一時領域の後片付けと保存済み進捗からの再開を接続する。

## 3. 設定の詳細

基本設計19.2節のキー名・既定値を採用する。旧設定のままならsingle。旧exeはcrawlを未知セクションとして拒否するため、新設定を旧exeへ配らない。設定サンプルの実変更は設定機能の実装PRで行い、各項目の用途・単位・ファイル／フォルダの別をコメントする。

| 項目                 | 検証・既定値                                                            |
| -------------------- | ----------------------------------------------------------------------- |
| crawl.mode           | 文字列singleまたはcontinuous。省略時single                              |
| crawl.wait_seconds   | `type(value) is int`、60～3600。省略時180                               |
| crawl.jitter_seconds | `type(value) is int`、0～30。省略時10                                   |
| crawl.progress_file  | 非空パス文字列。省略時LOCALAPPDATA/BlackLineCrawler/state/progress.json |
| crawl.result_dir     | continuousは非空パス文字列が必須。singleでは省略可能                    |

bool・小数・文字列を整数へ変換しない。不明セクション／キー、crawlが表でない指定、必須項目欠落もCONFIG_ERROR。singleでも指定した追加キーの型・範囲・パス条件を検証する。

既存のCDPループバック制限、ユーザー情報付きURLの拒否、タイムアウト検証、デバッグ環境変数の接続前拒否を維持する。進捗・結果の値は設定読込時に確定し、変更は手動再起動後に適用する。

### 3.1 パスと起動順

1. settings.toml所在を基準に相対パスを解決する。ドライブ相対・ドライブなしルート相対は拒否する。
2. output_dir／error_dir／result_dir／temporary_rootの一致・包含を拒否。progress_fileとcompletion_fileは別ファイルとし、これらフォルダの外に置く。両ファイルの親の共有は許可するが、一方のファイルが他方や他出力の親となる指定は拒否する。singleの省略result_dirは比較から除く。
3. 既存の解決済みパス・リンク・Windows長制限を出力先と生成ファイルに適用する。ディレクトリ位置にファイル、ファイル位置にディレクトリがある指定を拒否する。同期対象外の進捗・一時領域であることは運用確認とする。
4. 全構文・値・パス検証の成功後に必要フォルダを作成する。singleでは巡回用進捗を読まない・作らない、result_dirも作らない。
5. continuousでは既存記事と進捗を検証してからChromeへ接続する。進捗がないことと読込不可を区別する。進捗ファイル不在だけが初回。

設定不正ではCONFIG_ERRORのログを試み、終了コード1。Chrome接続・一覧取得・待機・進捗／記事／完了日時更新へ進まない。未検証のerror_dirを信頼せず、既存の代替出力と標準エラーを使う。固定文は違反キーと要求範囲を示し、設定値・ファイル全文・生例外は出さない。

## 4. 値オブジェクトとURL・階層

| 型案             | 値                                                                                                        |
| ---------------- | --------------------------------------------------------------------------------------------------------- |
| Target           | source_url、menu_name、menu_path。URLは正規化済み、menu_pathは記事自身を含む全階層                        |
| ObservedPosition | 現在行のURL・観測できた名称／階層。固定保存階層とは別のメモリ上の値                                       |
| PageOutcome      | kind=new／updated／unchanged／skipped。スキップ時は固定stage・reason_code。ブラウザや例外全文を持たせない |
| Progress         | 5節のJSON項目。読込検証後だけ制御に渡す                                                                   |

TargetのAPI照合用識別子・言語・版の永続化は11節で確定するまで追加しない。共通制御のダミーではAPI識別済みという明示的な結果を渡し、本番用の推測ロジックを作らない。

保持候補の具体化と残る条件は18.2節、合意した監視境界と残る条件は19節を参照する。これらは現行スキーマ案へ未確認値を追加したものではない。

URL同一性は現行normalize_urlを共通使用する。scheme・netlocは小文字化、フラグメントは除去し、パス・クエリ・末尾スラッシュは保持する。デフォルトポート除去、クエリ並べ替え、スラッグの推測変換は追加しない。ログだけlog_urlでクエリも除去する。

continuousの保存用menu_pathは`target.menu_path[:-1] + [実際の本文タイトル]`とする。親はURLなし見出し・起点より上の祖先も含めて固定する。取得画面が別の重複位置を現在項目としても、現在行のURLが対象と一致すれば固定一覧の最初の親階層を採用する。名称変更だけで別記事としない。現在行のURL不一致・欠落・複数現在行は抽出不成立として保存しない。認証APIの照合は現在行がない場合にも独立して判定できる方式を11節で確定する。

本文・画像・表示URL・canonical・現在行は取得内の前後で整合を確認する。表示URLの正規化不一致はURL_MISMATCH、canonicalの不一致や本文の途中変化はEXTRACTION_ERRORとし、いずれもcontinuousではスキップ。可視祖先欠落だけを理由に固定一覧の階層を組み直さない。

## 5. 進捗JSON

### 5.1 スキーマ案

UTF-8 BOMなし・LF、schema_versionは整数1。必須キーの欠落、未知キー、重複キー、非有限数、型の相違を拒否する。以下は**架空のURL・名称による例**。内部データの元URLをログ用にマスクしてから保存すると再開できないため、進捗とログの形式を分ける。

```json
{
  "schema_version": 1,
  "root_url": "https://example.invalid/docs/ja/root",
  "output_dir": "C:\\Example\\Knowledge",
  "cycle_id": "00000000000000000000000000000001",
  "started_at": "2026-10-26T09:00:00+09:00",
  "targets": [
    {
      "source_url": "https://example.invalid/docs/ja/root",
      "menu_name": "起点",
      "menu_path": ["上位", "起点"]
    }
  ],
  "next_index": 1,
  "phase": "cycle_complete",
  "counts": {"new": 1, "updated": 0, "unchanged": 0, "skipped": 0},
  "completion_to_write": "2026-10-26T09:00:10+09:00",
  "finished_at": "2026-10-26T09:00:10+09:00"
}
```

- cycle_idは一覧確定時に生成するUUIDの小文字32桁。再開時は再発行せず、履歴ファイル名へそのまま使用する。パス文字を許容しない。
- started_atはその一覧取得を開始した日時。新一覧が完成するまでは候補値をメモリだけに置き、旧一巡の値を上書きしない。
- root_urlは現在設定の正規化値との完全一致、output_dirは解決済みWindowsパスとして現在設定と同一であることを要求する。別起点・別保存先を自動移行しない。
- targetsは非空配列、先頭URLはroot_url、各URLは正規化済みで重複なし。menu_nameとmenu_path各要素は非空文字列で、末尾はmenu_nameに一致。構造は一覧確定時のものを保持する。
- 添字・件数はboolを除く非負整数。target件数はtargetsの長さから求め、進捗のcountsには持たせない。`next_index = new + updated + unchanged + skipped`、`next_index <= len(targets)`を要求する。
- started_at・finished_at・completion_to_writeは既存valid_datetimeと同様のタイムゾーン付き文字列、後2項目のみnull可。時刻の前後関係だけを状態整合の根拠にせず、OS時計の補正と処理順を区別する。

### 5.2 状態の整合条件

Nをtargets件数、iをnext_indexとする。初回のdiscovering状態を空一覧で保存する方式は採らず、進捗がない間は初回一覧取得として扱う。

| phase               | iと日時の制約                                                                    | 再開処理                                   |
| ------------------- | -------------------------------------------------------------------------------- | ------------------------------------------ |
| ready               | 0≦i＜N、finished_at=null、completion_to_write=null                               | targets[i]を取得                           |
| waiting（ページ間） | 0＜i＜N、finished_at=null。completion_to_writeは直前正常日時またはスキップのnull | 日時補完後に待機を最初から行う             |
| cycle_complete      | i=N、finished_at必須。completion_to_writeは最終ページ正常日時またはnull          | 日時補完、一巡結果確定、waitingへ保存      |
| waiting（一巡後）   | i=N、finished_at必須。completion_to_writeは最終ページ正常日時またはnull          | 日時・履歴の一致を確認／必要な補完後に待機 |
| discovering         | i=N、finished_at必須、completion_to_write=null。前一巡の一覧・件数を保持         | 追加待機せず新一覧取得                     |

completion_to_writeは「直前ページが正常ならその完了日時」であり、単なる未出力フラグではない。出力直後にnullにするためだけの進捗保存は行わない。同値なら日時ファイルを上書きしない。次のready／discoveringへの遷移でnullへする。スキップの確定ではnullにし、過去の完了日時ファイルを更新しない。JSONだけでは直前結果を完全復元できないため、null以外なら正常件数の合計が1以上であることも検証する。

破損・未対応バージョン・不整合・読込失敗はPROGRESS_ERRORで停止する。自動バックアップ復元や先頭への巻戻しは行わない。書込は同一親の一意な一時ファイルを排他的に作成し、flush→fsync→close→os.replace。置換前の失敗なら旧進捗を保持する。置換成立後の後片付け失敗や直後の中断では、保存呼出しが正常復帰しなくても新進捗が残る場合がある。再開時は正式名のJSONを再読込・検証して状態を決め、例外が出たことだけを理由に旧状態へ戻さない。いずれの失敗でも新しい完了日時を出力して続行せず停止する。電源断等を含む完全な耐障害性は保証しない。20.5節に境界確認を記録する。

## 6. 制御と確定境界

### 6.1 一巡の開始

初回は既存記事を走査してから一覧を取得する。discoveringからの次一巡でも既存記事を再走査する。一覧取得専用タブは起点だけを開き、列挙後に閉じて切断する。起点本文保存やページ件数に流用しない。

一覧取得・全件検証・タブ解放・切断が成功した後、新cycle_id、started_at、固定targets、i=0、件数0、ready、両補完日時nullをまとめて保存する。進捗保存に成功して初めて起点本文の通常取得を始める。失敗なら旧discoveringまたは進捗不在を保持し、途中一覧を使用しない。

### 6.2 正常ページ

1. 対象専用のUUID一時領域を作る。ページ専用タブで本文・全画像と必要なHTTP観測を完了し、作業タブを閉じ、Playwrightを停止して切断する。
2. 固定一覧の親階層と実本文タイトルをスナップショットへ反映し、文書生成・比較計画を作る。
3. 完成画像を最終配置へ反映し、Markdownを反映する。改名・移動なら新配置成功後に旧Markdownを削除する。無変更なら既存Markdownを上書きしない。
4. 成功した保存結果をURL対応表へ反映する。最終パスと実際に保存したメタデータを返す方法を採り、日時を再採取して別値を捏造しない。無変更は旧エントリを維持する。
5. 今回の一時領域だけを片付ける。ここまで成功した日時をcompletion_to_writeへ設定し、kindに対応する件数を1増加、iを1進める。最終対象なら同じ完了境界でfinished_atを設定する。
6. 非最終ならwaiting、最終ならcycle_completeを進捗へ置換保存する。
7. 保存済みcompletion_to_writeと同じ日時を完了日時ファイルへ出す。非最終は待機、最終は一巡結果の確定へ進む。

計画・保存失敗をスキップへ変換しない。画像の一部反映後に保存が失敗した場合、記事・画像を一括で元に戻さず停止する。保存後で進捗未確定なら再開時に同じURLを再取得する。new／updatedがunchangedとして確定し得る集計上の制約は合意済みであり、追加ジャーナルで元分類を保証しない。

### 6.3 スキップページ

最終反映前にだけスキップを選択できる。既存Markdown・画像・完了日時を変更しない。スキップJSONをerror_dirへ作り、タブ・接続・一時領域を片付ける。取得関数内でタブ解放済みの場合は二重解放しない。取得のfinallyで解放を試みた場合も、解放失敗は全体停止とする。

ログ保存と後片付けの両方が成功した場合だけskippedとiを各1増加し、completion_to_write=null、非最終waiting／最終cycle_completeとして進捗保存する。最終ならfinished_atも採取する。その後は正常ページと共通の待機／一巡結果確定へ進む。

ログ後・進捗前に停止すると同じ対象を再取得し、スキップログが複数残る可能性がある。ログ数を処理件数にせず、進捗の確定件数を一巡結果へ使用する。その場での再送や連続スキップ件数による停止は設けない。

### 6.4 一巡結果と待機

最終ページの進捗・必要な完了日時が成功してから、保存済みcycle_id・started_at・finished_at・countsで結果を作る。結果確定後、同じ一覧・件数・日時を保持してphase=waiting、i=Nを保存する。この保存に失敗したら待機／次一覧取得へ進まない。

待機は`B + randint(-J, J)`秒。毎回両端を含む一様な整数を抽選し、単調時計の期限まで最大0.5秒単位で待つ。処理時間やクラウド同期時間は待機に含めない。待機中はChrome接続を持たず、Ctrl+Cを受けられるようにする。

待機終了後は、非最終ならready、最終ならdiscoveringへ進捗保存し、completion_to_write=nullへする。最終では旧一巡のfinished_atを保持する。この保存が成功してから次ページ／次一覧取得を開始する。最終ページにも待機は1回だけであり、ページ待機と一巡後待機を重ねない。

再起動でwaiting／cycle_completeなら必要出力を補完して新しく抽選し、最初から待つ。残時間・予定時刻・抽選値は永続化しない。discoveringでの再起動は既に待機済みなので追加待機せず一覧を取り直す。

## 7. 保存・復旧・手動終了

Markdown形式、front matter、URLハッシュ8桁から4桁ずつ64桁までの衝突回避、created_at継承、画像全ハッシュ、相対参照、変更判定は既存契約を維持する。画像・本文が同じでもタイトル／親階層変更はrelocateとしてupdatedに含める。旧画像・削除記事・対象外記事は自動削除しない。

| 停止境界                        | 永続状態と再開                                                                  |
| ------------------------------- | ------------------------------------------------------------------------------- |
| 取得・変換途中／最終反映前      | readyの同じ対象を再処理。既存記事を保持                                         |
| 画像だけ反映                    | 同じ対象を再処理し、ハッシュ一致画像を再利用。不要画像は残す                    |
| Markdown保存後・旧配置整理前    | 重複URLがあれば既存走査で停止。人が内容・画像参照・created_atを確認し旧版を整理 |
| 保存／後片付け後・進捗前        | 同じ対象を再処理。完了日時は進めない                                            |
| 進捗保存後・完了日時前          | 対象を再取得せず、保存済み日時を補完して待機／結果確定                          |
| スキップ進捗後                  | 完了日時は変更せず待機／結果確定                                                |
| 結果確定後・waiting保存前       | cycle_completeから同名結果の一致を検証して再利用                                |
| 一巡後待機中                    | 同じ一巡の履歴を増やさず再抽選し待ち直す                                        |
| discovering保存後・新一覧保存前 | 旧一巡の一覧と件数を保持し、新一覧を再取得。待機を足さない                      |

Ctrl+Cはcontinuous最上位で扱い、ページ結果の確定を途中から推測して進めない。今回の作業タブ・接続・一時領域の片付けを試み、再起動時に正式名として残った進捗を検証して再開点とする。通常の手動終了は0、後片付けや既に発生した全体停止エラーがあれば1。KeyboardInterruptで既知のAUTH_ERROR等を成功扱いへ上書きしない。通常のCtrl+Cをページスキップとして記録しない。

強制終了・PC停止では後片付けと終了ログを保証しない。残留一時領域を別実行が自動削除しない。進捗リセットはアプリ停止確認→progress_fileを人が別名に退避→起点・保存先設定を確認→再実行の順。記事・画像・ログ・履歴を削除しない。

## 8. エラー分類とHTTP観測

continuousでは固定コードを持つページスキップ用例外（PageSkip案）と、全体停止用CrawlerErrorを区別する。stageや一般Exceptionだけからスキップを推測しない。分類不能はUNEXPECTED_ERRORで停止する。

| 分類                                   | 固定コード案          | 挙動                                         |
| -------------------------------------- | --------------------- | -------------------------------------------- |
| 主文書・明示画像・関連本文APIの401/403 | AUTH_ERROR            | 全体停止。転送やgoto失敗より優先             |
| 主文書の経路中302                      | HTTP_302_REDIRECT     | ページスキップ。既存の模型の理由コードを維持 |
| 主文書の301/303/307/308                | HTTP_REDIRECT         | ページスキップ                               |
| 転送なしの表示URL不一致                | URL_MISMATCH          | ページスキップ                               |
| 明示画像の302                          | HTTP_302_REDIRECT     | 全ページの更新を見送る                       |
| 明示画像の301/303/307/308 | HTTP_REDIRECT | ページ全体を保存せずスキップ。2026-10-26合意 |
| ページ通信失敗・404/429/500等          | PAGE_FETCH_ERROR      | ページスキップ                               |
| 画像通信・デコード失敗・非対応形式     | IMAGE_FETCH_ERROR     | ページスキップ                               |
| 本文／現在行抽出・前後整合不成立       | EXTRACTION_ERROR      | ページスキップ                               |
| Markdown変換不成立                     | CONVERSION_ERROR      | ページスキップ                               |
| CDP・タブ作成                          | BROWSER_CONNECT_ERROR | 全体停止                                     |
| 解放・切断・一時領域削除               | CLEANUP_ERROR         | 全体停止                                     |
| 一覧取得・完全性・境界不成立           | DISCOVERY_ERROR       | 全体停止                                     |
| 進捗読込・検証・保存                   | PROGRESS_ERROR        | 全体停止                                     |
| スキップ指定先出力失敗                 | SKIP_LOG_WRITE_ERROR  | 全体停止。代替ログだけでは続行しない         |
| 一巡結果読込・一致検証・確定           | CYCLE_RESULT_ERROR    | 全体停止                                     |
| 設定・既存資料・パス・保存・完了日時   | 既存コードを維持      | 全体停止                                     |

複数原因がある場合、観測済み401/403を認証の主原因として保持する。全体停止原因が1つでもあればPageSkipとして戻さない。後片付け失敗はsecondaryとして別停止ログも試み、元の失敗を隠さない。非認証のスキップ理由が複数なら、主文書転送（302があれば302コード）→URL不一致→取得・抽出・画像・変換の順で選び、任意の応答順に依存させない。

### 8.1 観測範囲と失敗境界

- 作業タブのgoto前に監視を登録。主フレームの主文書の応答経路を保持し、最終200でも途中転送を見逃さない。他タブ・子フレーム・Script・解析サービスを混入させない。
- 主文書の401/403は経路のどこでも停止。gotoが例外でも観測済み認証情報を一般通信エラーで上書きしない。
- 明示画像は現行同様のCookie共有要求、max_retries=0、max_redirects=0を使用し、200だけをデコード・保存候補にする。301/302/303/307/308は転送を追わずページ全体をスキップし、次の一巡で再取得する。302はHTTP_302_REDIRECT、追加4種はHTTP_REDIRECT。関連401/403があれば全体停止を優先する（2026-10-26追加合意）。
- 通信・response.body取得と画像デコードの失敗はページ単位。一時ファイル作成・書込・読込・削除は別try境界で全体停止とする。ローカルOSErrorをIMAGE_FETCH_ERRORへ包み直さない。
- 関連本文APIはタブ・フレーム・既知の正確な経路／メソッド・対象記事の識別を組み合わせる候補。同一ホストだけ、API名の部分一致だけ、Refererだけでは採用しない。
- DOM準備だけ／固定2秒待機／一般的な通信静穏だけをAPI監視完了の保証としない。19節の合意に従い監視をタブ解放まで維持し、解放・切断後に結果を確定する。必須API集合・版の識別・期限切れ分類は11節の保留条件。
- 一覧確定前にはページスキップを適用しない。転送・通信・メニュー検証失敗ならDISCOVERY_ERROR、識別済み401/403ならAUTH_ERRORで全体停止する。

## 9. 運用JSONと出力の冪等性

全JSONはUTF-8 BOMなし・LF、日時はタイムゾーン付きISO 8601。固定stageはconfig／scan／discover／fetch／convert／compare／save／cleanup／progress／completion／cycle_result／waitを使用する。未検証の例外文・レスポンス本文・転送先・APIクエリ・記事IDをメッセージへ含めない。

### 9.1 停止・スキップ

停止JSONは既存5項目occurred_at／source_url／stage／error_code／messageを維持し、error-UTC日時-UUID.jsonへ保存する。追加コードには固定文を用意する。指定先→exe所在→標準エラーの既存代替経路を使い、ログ失敗の再帰出力はしない。

スキップJSONはskip-UTC日時-UUID.jsonの一意なファイルへ排他的に作成する。必須項目は次のとおり。

| 項目         | 値                         |
| ------------ | -------------------------- |
| record_type  | page_skip                  |
| occurred_at  | スキップ判定時の日時       |
| source_url   | log_url(target.source_url) |
| stage        | 失敗した処理段階           |
| reason_code  | 8節のスキップ固定コード    |
| message      | コードごとの固定文         |
| cycle_id     | 保存済み一巡識別子         |
| target_index | 対象の0始まり添字          |
| retry_policy | next_cycle                 |

ログは1件ごとflush・fsync・closeの成功を確認する。スキップ指定先に書けなければSKIP_LOG_WRITE_ERRORで停止し、可能な停止ログの代替出力を試みる。ファイル名とrecord_typeで停止と識別できるようにし、Power Automate側の変更・Teams等への直接通知は本作業へ含めない。

### 9.2 一巡結果

result_dir/cycle-<cycle_id>.jsonへ一巡1ファイルを保存する。項目はrecord_type=cycle_result、schema_version=1、cycle_id、root_url（ログ用）、started_at、finished_at、status、counts。countsはtarget／new／updated／unchanged／skippedの非負整数で、target=Nとし、他4項目の合計と一致させる。skipped=0はcompleted、1以上はcompleted_with_skips。停止した未完了一巡の完了結果は作らない。

同一親の一意な一時名で完成・flush・fsync・close後、Windowsの宛先既存時に失敗するrenameで正式名を確定する案とする。上書きするos.replaceを履歴確定には使わない。実装時に対象Windowsのダミーで「既存履歴を上書きしない」ことを確認する。正式名が既にあれば重複キー・型を含め検証し、全項目が期待値と一致する場合だけ再利用する。不正・不一致は停止。正式名がなく一時名だけ残った場合は完成とみなさず、保存済み進捗から再生成する。

履歴は進捗で確定した分類を表す。保存後・進捗前の停止でnew／updatedがunchangedになる制約があるため、保存ファイル操作回数の監査用途には使わない。途中停止は停止ログ・進捗を確認し、同じ一巡を再開して完了時に1ファイルを残す。

## 10. メニュー列挙の設計候補

以下は共通の入出力契約と候補アルゴリズム。実サイトの汎用全件列挙を確定したものではない。

1. 起点を1回開き、起点URLと現在行を対応させ、全祖先・言語・配下境界の根拠を確保する。URLパスの前方一致で親子関係を決めない。
2. メニュー行の位置・level・兄弟位置／件数・展開状態・名称・URLの有無を観測する。採寸用要素を除外する。URLなし行を欠落とせず階層に残す。正確な行セレクター・URLなし名称の識別は11節で確定する。
3. 起点配下の展開アイコンだけを操作する。記事リンクをクリックして本文巡回しない。展開で位置が変わったら旧座標系を破棄し、新しい展開状態の観測へ切り替える。
4. 固定した展開状態でスクロール範囲を統合し、画面外になった祖先を保持する。同じURLの別位置は完全性検証が済むまで別行として残す。
5. 全兄弟の位置1～件数、祖先の連続性、起点配下の終端、未展開枝なし、観測間の構造整合を検証する。終端到達や変化停止だけで成功にしない。途中変更・欠落・位置の矛盾・期限超過は停止する。
6. 完全な木を親→子孫→次の同階層へ走査し、同一サイト・同言語のURLを持つ行だけ取得対象にする。URLなし見出しは祖先に保持する。本文リンク・外部・別言語を追加しない。
7. 最後にnormalize_urlによる重複を除き、最初の位置と全階層をTargetへコピーする。先頭が起点で非空であることを確認し、タブ解放・切断成功後に返す。

調査用の最大回数・45秒等を根拠なく本番の設定や完全性保証に転用しない。列挙期限・展開後の再観測条件も、全件判定方式と一緒に確定する。期限到達時の部分一覧を成功として返すことはない。

### 20.1 保存結果とメモリ上のURL対応表

`commit_save(...) -> ExistingDocument`へ戻り値を追加する案とする。singleは戻り値を使用せず、既存の呼出しを維持できる。unchangedでは検証済みplan.existingを返す。new／update／relocateでは画像・Markdown反映と必要な旧配置整理を終え、最終Markdownのread_metadataで検証した実メタデータと最終パスを返す。読込失敗は全体停止し、日時・hashを推測して生成し直さない。

crawlerは戻り値を得た後だけ`existing[target.source_url]`を置き換える。SavePlan.kindの写像はnew→new、update／relocate→updated、unchanged→unchangedとする。保存関数の戻り値を進捗確定と混同せず、その後の一時領域片付けと進捗保存まで成功して初めて件数を確定する。保存後・メタデータ再読込前の失敗でも保存済み記事を巻き戻さず、次の起動で通常の走査から照合する。

### 20.2 JSONの共通規則と結果の一致検証

進捗・一巡結果の出力は`json.dumps(..., ensure_ascii=False, indent=2, allow_nan=False) + LF`のUTF-8 BOMなしとする。読込は重複キーを検出するobject_pairs_hook、NaN／Infinity等を拒否するparse_constantを用い、その後にスキーマの型・値を検証する。整数はboolを認めず、日時はオフセットを持つ文字列だけを認める。ファイル名・パス由来の値を無検証でJSONへ引き継がない。

一巡結果の最上位キーは9.2節の8項目、countsはtarget／new／updated／unchanged／skippedの5項目に限定する。schema_versionは整数1、record_typeはcycle_result、cycle_idは進捗の32桁小文字UUIDと一致させる。開始・終了日時、ログ用root_url、件数、statusの全項目は保存済み進捗から求める。再出力時に時刻を採り直さない。

同名ファイルの再利用は、重複キー・未知キー・欠落・型・状態を検証した後に意味上の全項目一致で判定する。インデントやキー順だけの違いは不一致理由にしない。ただし`true == 1`のようなPythonの値比較だけで型検証を省略しない。件数不一致・completedとskippedの矛盾・別cycle_idはCYCLE_RESULT_ERROR。既存ファイルを修正して一致させず停止する。

架空の一巡結果例（1件スキップ）は以下のとおり。

```json
{
  "record_type": "cycle_result",
  "schema_version": 1,
  "cycle_id": "00000000000000000000000000000002",
  "root_url": "https://example.invalid/docs/ja/root",
  "started_at": "2026-10-26T09:00:00+09:00",
  "finished_at": "2026-10-26T09:10:00+09:00",
  "status": "completed_with_skips",
  "counts": {"target": 3, "new": 1, "updated": 0, "unchanged": 1, "skipped": 1}
}
```

履歴の同名確認は現在設定されたresult_dir内で行う。進捗は過去のresult_dirを保持していないため、過去ディレクトリを探索して移行する処理は追加しない。同じ一巡の途中に運用出力先を変える場合の履歴整理はアプリの自動移行対象にせず、人が保存先を確認する。

### 20.3 完了日時の補完と進捗遷移

`write_completion(path, completed_at=None)`はsingleで省略された場合だけ現在日時を採取する。continuousでは検証済みのcompletion_to_writeを必ず渡す。期待バイト列は日時のUTF-8とLFのみ。既存ファイルが同じバイト列なら書込を省略し、不在または異なる場合は同一親の一時名から置換する。既存ファイルを読めない場合はCOMPLETION_WRITE_ERRORとして停止する。completion_to_write=nullのスキップではファイルの読込も書込も行わない。

waitingへ入る前に必要な日時補完を終え、一巡後なら一巡結果も確定・検証する。再開時にどちらかが失敗したら、待機や次ページへ進まない。日時を補完しただけでは進捗を再保存してnullにせず、5.2節どおりready／discoveringへ移る時点でnullにする。待機開始時刻・抽選値・残時間は保存しない。

### 20.4 固定メッセージと出力失敗

既存停止コードの文言は既存MESSAGESを維持する。追加の停止コードは次の固定文とする。生の例外文や設定値を補間しない。

| コード | 固定メッセージ |
| --- | --- |
| DISCOVERY_ERROR | 対象一覧を確定できません。起点・メニュー構造・通信状態を確認してください。 |
| PROGRESS_ERROR | 進捗を読込・検証・保存できません。起点・保存先・進捗ファイルを確認してください。 |
| SKIP_LOG_WRITE_ERROR | スキップログを保存できません。ログ出力先の権限・空き容量を確認してください。 |
| CYCLE_RESULT_ERROR | 一巡結果を確定できません。保存先と既存の同名結果を確認してください。 |

スキップJSONのmessageは停止用文言と分け、次の固定文を使う。

| reason_code | 固定メッセージ |
| --- | --- |
| HTTP_302_REDIRECT | HTTP 302転送を検出したためページ全体をスキップしました。次の一巡で再取得します。 |
